# 项目文件与持久化

> 状态：决定 1–7 已于 2026-10-22 确认；M6 和 M5b 已按本稿实现
> 范围：项目文件格式与读写（M6）、最近项目与设置、派生结构的来源记录（M5b 用到）。
> 相关：[晶体学数据模型](crystallography-model.md)第 6 节（文档层）、7.8–7.9 节（晶胞变换、超胞）、7.12 节（撤销）· [界面外壳](ui-shell.md)第 3 节（边栏）、4.1 节（顶栏的保存状态）· [AI 集成](ai-integration.md) 5.1 节（无界面模式写项目文件）、6.4 节（会话记录）· [产品路线图](../roadmap.md)第 15 节（项目系统与来源记录）

## 1. 目标

| 要求 | 说明 |
|---|---|
| 状态完整恢复 | 关闭再打开项目（路线图 M6 的验收），结构、测量、来源记录、上次打开的是哪个结构、每个结构的视角和显示模型都回来 |
| 可以搬动 | 项目整个复制到别的目录或别的机器上照样能打开，项目内部只用相对引用 |
| 有版本 | 每个项目写明格式版本；新版本的应用能打开旧项目 |
| 不依赖界面 | 读写在纯 Rust 的 crate 里，MCP 的无界面模式、以后的命令行和测试都能用 |
| 不静默丢数据 | 读不了的部分报告出来，其余照常打开；保存失败时内存里的数据不动 |
| 能扩展 | XRD 谱图、显微图像、助手会话记录以后放进同一个项目，不改已有部分 |

**不在 v0.1**：自动保存与崩溃恢复、多个进程同时写同一个项目（MCP 无界面模式写项目文件时再加锁，v0.3）、项目内的文件夹分组、项目和结构改名、从项目里删除结构（见第 13 节末尾）。

## 2. 存什么

| 内容 | 存在哪里 | 进撤销栈 | 改动后显示"有未保存的更改" |
|---|---|---|---|
| 结构（`Structure`） | `structures/<id>.json` | 是 | 是 |
| 测量（含"已失效"标记） | 同上 | 是 | 是 |
| 编辑记录（已提交的命令） | 同上 | — | 随编辑 |
| 条目列表、名称、来源记录 | `project.json` | 否 | 是（新增结构时） |
| 导入文件的原样副本 | `sources/` | — | — |
| 视图状态：相机、显示模型、右侧面板、打开的结构 | `view.json` | 否 | 否，保存和关闭项目时顺带写入 |
| 撤销 / 重做栈 | 不存 | — | — |
| 导入诊断 | 不存，打开结构时由源文件副本重新解析得出 | — | — |
| 派生数据（展开、对称性分析、键） | 不存，按晶体学设计稿第 5 节现算 | — | — |
| 会话状态：选区、测量模式、悬停 | 不存 | — | — |
| 设置（主题、语言） | 配置目录 `settings.json` | — | — |
| 最近项目、退出时打开着的项目 | 配置目录 `state.json` | — | — |

撤销栈不存：撤销是会话内的操作，逆命令里带着整份位点甚至整个结构的快照，存下来体积大、还要为它定格式；存了也只是让"上次会话的撤销"在下次可用，没有哪个桌面科学软件这样做。

## 3. 磁盘布局

**决定 1：一个项目是一个目录，名称以 `.mwproj` 结尾，里面是一个清单文件和按对象分开的文件。**

```text
TiO₂ 相研究.mwproj/
├── project.json                 清单：格式版本、项目 ID 和名称、条目列表（ID、类型、名称、来源记录）
├── structures/
│   ├── 3f6c1d2e-….json          一个结构文档的内容：结构、测量、编辑记录
│   └── 9a0b44c7-….json
├── sources/
│   └── 5e8d…（SHA-256）.cif     导入文件的原样副本，按内容哈希命名
└── view.json                    视图状态；删掉它不影响数据
```

- 目录由应用管理：应用只读写这四类文件，目录里其他文件不碰（用户可以自己放笔记、原始数据）；清理不再引用的文件时只清理 `structures/` 和 `sources/` 里符合命名规则的文件。
- 后缀 `.mwproj` 让"打开项目…"能认出它；v0.3 打安装包时在 macOS 上登记为文档包（document package），访达里显示成一个文件、双击打开，Windows 和 Linux 上仍是普通目录。
- 文本全部是 UTF-8 的 JSON。外层缩进两格；列表里的每一项（一个位点、一条测量、一条编辑记录、一个清单条目）写在一行里，所以改一个位点只改一行，文件也不会因缩进膨胀。同样的内容总是写出同样的字节（字段顺序由类型定义固定），便于放进 git 比较差异。

**理由**：

- 以后的模块有大文件：XRD 原始谱、显微图像。目录里每个对象一个文件，保存时只重写改过的文件，二进制数据原样放，不用 base64 塞进 JSON。
- 导入文件的副本（第 7 节）原样放进 `sources/`，字节不变，哈希可以直接核对。
- 外部程序（脚本、MCP 无界面模式、git）不需要专门的库就能读。
- 助手的会话记录（AI 集成 6.4 节）适合追加写的 JSON Lines，可以作为一种新条目放进 `sessions/`，不影响已有文件。

**备选**：

| 方案 | 不选的原因 |
|---|---|
| 单个 JSON 文件 | 最容易发给别人，保存天然原子（写临时文件再改名）。但每次保存重写全部内容；源文件副本和以后的图像、谱图都得编码进去，文件会很大；一处损坏可能整个打不开 |
| 单个 zip 包（像 `.docx`、`.3mf`） | 好分享，能装二进制。但改一个结构就要重写整个包（zip 不适合原地更新），外部工具读写要解包，git 比较不了差异 |
| SQLite 单文件 | 原子、能装大块数据。但不透明、比较不了差异，要引入带 C 代码的依赖；对现在的数据量是过度设计 |
| 普通目录，清单名为 `project.mwproj` | 项目目录可以是任意名字的文件夹。但应用管理的子目录和用户自己的文件混在一起；访达里也没法当成一个文件 |

单目录的缺点是发给别人时要整个目录一起打包；v0.3 可以加"导出为压缩包"。

## 4. 格式版本与迁移

**决定 2：整个项目用一个整数版本号，写在 `project.json` 里；新版本应用按顺序迁移旧项目，旧版本应用拒绝打开新项目。**

- 当前版本为 1。目录里所有文件都由同一版本的写出代码生成，所以只在清单里记一个版本；`view.json` 和配置目录里的文件各有自己的版本号，因为它们可以单独丢弃。
- **任何**会改变写出内容的改动都升版本，包括只加一个可选字段。理由：v0.x 期间旧版本的应用遇到不认识的字段只会忽略，保存时就把它丢了。
- **打开更新版本的项目**：拒绝，提示"这个项目由更新版本的 Materials Workbench 保存（格式版本 N），请升级后再打开"。不做只读打开，避免看上去能用、保存时却丢数据。
- **打开旧版本的项目**：读成 `serde_json::Value`，依次执行 `v1 → v2`、`v2 → v3`……的迁移函数，再按当前类型解析。迁移只在内存里进行，项目标为"有未保存的更改"；第一次保存前，把要被覆盖的 JSON 文件原样复制到 `backup/format-v{旧版本}/`（源文件副本不会被覆盖，不复制），然后按新格式写出。
- **测试**：每个发布过的版本都留一份测试项目（`tests/fixtures/projects/v1/` 等），测试要求它们都能被当前代码打开、内容与预期一致。随应用附带的示例项目（第 11 节）同时就是当前版本的测试项目。
- v1.0（路线图里"稳定的项目格式"）之前格式可以随意改，但迁移函数照写，因为 v0.1 起仓库就公开，可能已经有人存了项目。

**备选**：每种文件各自带版本号——以后 XRD 文件可以单独升级。但一个项目里的文件总是一起写出的，分开的版本号只多出"组合是否兼容"的问题。语义化版本（主版本不兼容、次版本兼容）——要保证旧应用能安全地保留不认识的字段才有意义，v0.x 不做。

## 5. 清单 `project.json`

```json
{
  "format": "materials-workbench/project",
  "version": 1,
  "writer": "Materials Workbench 0.1.0",
  "id": "c0a8012e-5a1f-4c39-9b52-0f1d5d6e2a77",
  "name": "TiO₂ 相研究",
  "entries": [
    {
      "id": "3f6c1d2e-8b0a-4f5e-a1d2-6c7b8e9f0a1b",
      "kind": "crystal_structure",
      "name": "金红石",
      "provenance": { "import": { … } }
    },
    {
      "id": "9a0b44c7-1e2d-4c3b-8a9f-0e1d2c3b4a59",
      "kind": "crystal_structure",
      "name": "金红石 2×2×2 超胞",
      "provenance": { "derived": { … } }
    }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `format` | 固定字符串，用来认出这是项目清单 |
| `version` | 格式版本（第 4 节） |
| `writer` | 写出它的应用和版本，只用于排查问题 |
| `id` | 项目 ID（UUID v4），创建时生成，以后不变；配置目录里的最近项目和以后的 MCP 用它认出同一个项目 |
| `name` | 项目名，显示在边栏和顶栏。默认取目录名去掉 `.mwproj`，两者以后可以不同 |
| `entries` | 条目，顺序就是边栏里的顺序 |
| `entries[].id` | 条目 ID（UUID v4），对应 `structures/<id>.json`；永不复用 |
| `entries[].kind` | 条目类型；v1 只有 `crystal_structure`。以后的 `xrd_pattern`、`micrograph`、`assistant_session` 各自有目录 |
| `entries[].name` | 显示名 |
| `entries[].provenance` | 来源记录（第 7 节） |

- **ID 用 UUID**：以后在项目之间复制结构、合并项目时不用重新编号，也不用改写引用它的来源记录。会话里用的 `StructureEntryId`（`u32`，能力注册表和界面在用）在打开项目时分配，不写进文件，所以 `mw-automation` 的接口不用改。
- **名称和来源记录放清单里，内容放对象文件**：打开项目只读清单就能列出边栏（包括"派生"标记），结构文件等打开那个结构时再读（v0.1 也可以打开项目时全部在后台读完，格式不限制）。编辑结构只改它自己的文件，不改清单。

## 6. 结构文档 `structures/<id>.json`

```json
{
  "structure": {
    "cell": {
      "a": { "value": 4.594 }, "b": { "value": 4.594 }, "c": { "value": 2.959 },
      "alpha": { "value": 90.0 }, "beta": { "value": 90.0 }, "gamma": { "value": 90.0 }
    },
    "operations": ["x,y,z", "-x,-y,z", "-y+1/2,x+1/2,z+1/2", "…"],
    "space_group": { "hm_symbol": "P 42/m n m", "it_number": 136 },
    "sites": [
      {
        "id": 1,
        "position": [0.0, 0.0, 0.0],
        "occupants": [
          { "label": "Ti1", "species": { "element": "Ti", "symbol": "Ti" }, "occupancy": { "value": 1.0 },
            "adp": { "isotropic": { "value": 0.0061, "su": 0.0002 } } }
        ]
      },
      {
        "id": 2,
        "position": [0.3048, 0.3048, 0.0],
        "position_su": [0.0002, 0.0002, null],
        "occupants": [ … ]
      }
    ],
    "tolerances": { "position": 0.01, "symprec": 0.01, "short_contact": 0.5 }
  },
  "measurements": [
    { "measurement": { "distance": [ { "site": 1, "member": 0, "cell": [0, 0, 0] },
                                      { "site": 2, "member": 0, "cell": [0, 0, 0] } ] },
      "stale": false }
  ],
  "edits": [
    { "edit": { "command": "set_cell", "values": { "a": 4.6 } } },
    { "add_measurement": { "distance": [ … ] } }
  ]
}
```

示例为了易读把位点拆成了多行；实际写出时每个位点、每条测量、每条编辑记录各占一行（第 3 节）。

**决定 3：结构直接用 `mw-crystal` 领域类型的 serde 形式，并用快照测试把它固定下来，不另写一套"文件格式类型"。**

- `Site`、`Occupant`、`Species`、`Measured`、`CellParams`、`AtomRef`、`Measurement`、`Command` 在 M4 已经有 serde（编辑命令要序列化），格式与它们一致；`Structure`、`Lattice`、`Symmetry`、`SpaceGroup`、`Tolerances` 补上。
- **对称操作写成 CIF 的 xyz 记法字符串**（`"-y+1/2,x+1/2,z+1/2"`）：整数矩阵加有理平移，精确、紧凑、人能读，读回用现有的 `SymOp::parse`。写出全部操作（含定心平移），顺序与内存里一致——`AtomRef` 的成员编号依赖操作顺序（晶体学设计稿 5.1 节），顺序变了测量就会指错原子。读回时做群封闭检查（`Symmetry::new`）。
- **晶胞**写六个参数，各带可选的 s.u.；以后有显式朝向（POSCAR 导入，晶体学设计稿 4.2 节）时加可选的 `orientation`，标准朝向不写。
- **浮点数**：serde_json 用最短的能精确读回的十进制表示（ryu）写出；读的一侧默认只求"足够接近"，要开启它的 `float_roundtrip` 特性（工作区 `Cargo.toml`）才逐位相同——实现时发现 `0.09759999999999999` 不开启时读回成 `0.0976`。吸附后的 1/3 写成 `0.3333333333333333`。不会出现 NaN、无穷（模型的约束排除了它们）。
- **省略空值**：`None` 和空列表不写（`position_su` 全空、`oxidation`、`disorder`、`adp`、`su`），读时补默认值。这同时改变编辑命令的 JSON（更短），读旧写法仍然兼容。按第 3 节的写法，一个 10 万原子的 P1 结构约 15 MB。
- **读回时校验模型的硬约束**：操作集在反序列化时检查（含单位元、可逆、封闭）；其余由 `Structure::validate` 检查：晶胞成立、容差为正、位点 ID 和原子标签唯一、每个位点至少一个占位者、坐标是有限数、占位率大于 0（大于 1 在导入时只是警告，所以不算错）。不满足时这个结构打不开，报告文件名和原因，项目里其他结构照常打开。
- **快照测试**：示例项目里每个结构的 JSON 与测试里的预期文本逐字比较。改了领域类型的字段名或形状，测试失败，提醒去升版本、写迁移。

**备选**：在项目文件 crate 里另定义一套与领域类型一一对应的 DTO，读写时转换——领域类型可以随意重构而不影响格式。不选：类型数量翻倍；编辑命令（`Edit` 里带着 `Site`、`Occupant`）本来就要序列化进编辑记录，DTO 也得覆盖它们；快照测试已经能防止无意中改了格式。将来领域类型和格式真的需要分开时，再在出问题的类型上加 DTO。

**测量**按 `CrystalDocument::annotations()` 原样存，包括"已失效"标记，所以删除位点后保存、再打开，失效的测量还在。打开时如果 `AtomRef` 指向不存在的位点或成员，标为已失效，不丢弃。

**编辑记录**见第 7.3 节。

## 7. 来源记录

路线图第 15 节要求"每个对象记录来源（导入的文件、派生的操作），支持复现"。每个条目在清单里有一项 `provenance`，三种之一：

### 7.1 导入

```json
"provenance": {
  "import": {
    "format": "cif",
    "file_name": "rutile.cif",
    "path": "/Users/me/Downloads/rutile.cif",
    "sha256": "5e8d3b…",
    "block": "rutile",
    "imported_at": "2026-10-22T08:15:00Z",
    "structure_sha256": "a1f0c2…"
  }
}
```

**决定 4：导入时把源文件原样复制进 `sources/<sha256>.<扩展名>`。**

- `sha256` 是源文件字节的 SHA-256（小写十六进制），也是副本的文件名：同一个文件里的多个数据块、重复导入同一个文件，都只存一份。
- `path` 是导入时的绝对路径，只作记录（"从哪里来的"），打开项目时不访问它。注意：把项目发给别人时，这个路径会带上本机的用户名。
- `block` 是数据块名，配合副本就能找到当初读的是哪一块。
- `structure_sha256` 是导入时结构的规范 JSON（第 6 节的 `structure` 对象，紧凑写法）的 SHA-256。导出 CIF 时用它判断"结构改过没有"：没改过才写回未识别的字段（晶体学设计稿第 6 节）。现在的做法是和导入时的结构直接比较，存了哈希就不必在项目里另存一份导入时的结构。格式迁移后哈希可能对不上，这时按"改过"处理——只是少写回未识别的字段，并照常在通知里列出。
- **导入诊断和保留的字段不存**：打开结构时用 `mw_crystal_io::cif::read` 重新解析副本，取同名数据块的诊断和 `CifFields`。诊断带的行号就是副本的行号。如果以后的解析器给出不同的诊断，显示的是新的结果；项目里存的结构才是事实来源，不会因此改变。
- 副本不见了（用户手动删了）时，结构照常打开，诊断标签页说明源文件副本缺失，导出 CIF 不再写回描述性字段。

**理由**：项目自成一体，搬到别的机器上导出的 CIF 仍带着出版信息；可以随时核对副本没被改过；不用把 `mw-crystal-io` 内部的 `CifFields` 定成项目格式的一部分。代价是项目体积多了源文件大小（CIF 通常几十 KB，嵌了衍射数据的可达几十 MB）。

**备选**：只记路径和哈希，不复制——项目小，但源文件一移动或删除，诊断和保留字段就没了，项目也就不能"复现"。把 `CifFields` 和诊断序列化进结构文件——不依赖副本，但要为两套内部类型定格式，而且原始文本才是最完整的来源。

### 7.2 派生

```json
"provenance": {
  "derived": {
    "from": "3f6c1d2e-8b0a-4f5e-a1d2-6c7b8e9f0a1b",
    "from_name": "金红石",
    "from_structure_sha256": "a1f0c2…",
    "operation": { "make_supercell": { "matrix": [[2, 0, 0], [0, 2, 0], [0, 0, 2]] } },
    "derived_at": "2026-10-22T08:20:00Z"
  }
}
```

- `from`：来源条目的 ID。来源以后被删除也照样保留这条记录。
- `from_name`：派生时来源的名字，来源已删除时显示用。
- `from_structure_sha256`：派生时来源结构的哈希。界面可以据此说明"来源在派生之后改过"。
- `operation`：生成它的操作和全部参数，足以重做一遍。v1 有 `make_supercell`（整数矩阵 M，行优先，晶体学设计稿 7.9 节）；以后有 `transform_cell`（有理矩阵 P 和原点 p）、`symmetrize` 等。转为 P1 是否也生成新结构，见第 13 节的决定 6。

### 7.3 编辑记录

**决定 5：结构文件里存已提交命令的序列（`edits`），作为记录，不在打开时回放。**

- 内容是从导入或派生以来，每次会话里 `CrystalDocument::history()` 给出的命令（编辑和测量的增删），按顺序追加。保存时写出"打开时读到的记录 + 本次会话已提交的命令"；撤销掉的命令不在 `history()` 里，自然不会写出。
- 它只是记录：打开时不回放，存的结构才是事实来源。所以解析器、命令语义在以后的版本里变了也没关系。
- 用处：晶体学设计稿 7.12 节说的"导出成操作记录用于复现"、以后的 Python 回放和历史面板，以及 AI 集成 6.4 节的会话记录可以引用其中的命令。
- 一条命令通常几十到几百字节；即使编辑上千次也只有几百 KB。

**备选**：不存编辑记录，只存导入或派生的来源——格式更小，但"这个结构是怎么从源文件变成现在这样的"就只能靠人记。

### 7.4 新建

`"provenance": { "created": { "created_at": "…" } }`：在应用里从空白新建的结构。v0.1 没有这个入口，先留出类型，"添加位点"（v0.2）之后才有意义。

## 8. 视图状态 `view.json`

```json
{
  "version": 1,
  "open": "3f6c1d2e-8b0a-4f5e-a1d2-6c7b8e9f0a1b",
  "entries": {
    "3f6c1d2e-8b0a-4f5e-a1d2-6c7b8e9f0a1b": {
      "camera": { "yaw": 0.6, "pitch": 0.35, "half_height": 6.2, "target": [0.0, 0.0, 0.0] },
      "display_model": "ball_and_stick",
      "panel": "properties",
      "panel_open": true
    }
  }
}
```

- `open`：离开项目时打开的是哪个结构。
- 每个结构的相机（`OrbitCamera` 的转角、缩放和中心，场景半径打开时重新算）、显示模型、右侧面板的标签页和是否显示。
- 旋转视图、切换显示模型**不**标记"有未保存的更改"（晶体学设计稿第 1 节原则 4：视图状态不进撤销栈）。`view.json` 在保存项目、关闭项目和退出应用时写入；写不进去（只读位置）时忽略。
- 读不了（版本不对、内容坏了、条目已删除）时直接丢弃，用默认视图，不提示。
- 放在项目里而不是配置目录里：路线图 M6 写明项目保存视图状态；项目搬到别的机器上视角还在；示例项目可以带着挑好的视角。用 git 管理项目的人可以把它加进 `.gitignore`。

## 9. 保存

- **项目是保存的单位**：⌘S 保存当前结构所在的整个项目；⇧⌘S"另存为…"把项目写到新位置，之后编辑的就是新位置的项目。
- **未命名项目**：没有打开任何项目时打开文件、或"新建项目…"，得到一个只在内存里的"未命名项目"（导入的文件字节也留在内存里）。第一次保存时用系统保存面板选位置和名字，建立 `名字.mwproj` 目录。
- **有没有未保存的更改**：
  - 结构：`CrystalDocument` 记下保存时撤销栈顶那一步的编号（保存点）；当前栈顶不是它就是"有未保存的更改"。撤销回保存点时又变回"已保存"。
  - 项目：新增了结构（导入、派生），或迁移过格式。
  - 顶栏显示当前结构**所在项目**的状态，因为 ⌘S 保存的是整个项目；边栏里有未保存更改的结构在名字后加一个圆点。
- **写入顺序**：
  1. 新的源文件副本（按哈希命名，已有的不重写）；
  2. 改过的结构文件；
  3. `project.json`（最后写，相当于提交）；
  4. 删除清单里不再引用的结构文件、没有结构引用的源文件副本；
  5. `view.json`。

  每个文件都先写到同目录的临时文件，再改名替换，所以单个文件不会写一半。中途失败时停下，报告失败的文件和原因；已经写好的文件是新内容，内存里仍是"有未保存的更改"，可以重试或另存为。
- **在后台线程写**：序列化在界面线程上做（拿到结构的 `Arc` 快照后很快），写文件在后台任务里做，写完回到界面线程更新保存点。
- **关闭项目或退出应用时有未保存的更改**：弹对话框"取消 / 不保存 / 保存"。退出时有几个项目没保存就在一个对话框里列出它们，`保存`依次保存（未命名的逐个弹保存面板），全部成功才退出，取消面板或保存失败就停下。
- **只读位置**（例如以后装在应用包里的文件，或权限不够的目录）：保存失败，提示用"另存为…"。

## 10. 配置目录

**决定 7：设置和最近项目放在系统的配置目录里，用 JSON。**

| 平台 | 目录（`dirs::config_dir()` + `materials-workbench`） |
|---|---|
| macOS | `~/Library/Application Support/materials-workbench/` |
| Linux | `~/.config/materials-workbench/`（遵循 `XDG_CONFIG_HOME`） |
| Windows | `%APPDATA%\materials-workbench\` |

- `settings.json`：`{ "version": 1, "theme": "light", "language": "zh-CN" }`。改设置时立即写入；设置对话框里"选择不会保存"的说明删掉。
- `state.json`：`{ "version": 1, "recent": [ { "path": "…", "id": "…", "name": "…", "opened_at": "…" } ], "open": ["…"], "active": "…" }`。最近项目最多 10 个，最新的在前，按项目 ID 去重（项目被移动后再打开，旧路径的那一项被替换）；`open` 和 `active` 是退出时打开着的项目和当前项目，下次启动时恢复。路径已不存在的最近项目在列表里仍显示，点击时提示并移除。
- 两个文件读不了、版本不认识时用默认值并写一条日志，绝不因此启动失败。
- 示例项目的可写副本放在数据目录（`dirs::data_dir()` + `materials-workbench/samples/`，macOS 上与配置目录相同）。
- 用 `dirs` crate 取目录（MIT / Apache-2.0，已在依赖树里）。macOS 上也同时调用 GPUI 的 `add_recent_document`，让程序坞菜单里出现最近的项目。

**备选**：TOML 写设置——手改更友好，但设置都由界面改，和项目文件用同一种格式更省事。放进项目目录——设置是应用级的，不随项目走。

## 11. 示例项目

内置示例（`mw-crystal/src/sample.rs` 里手写的金红石、超胞、SrTiO₃）改为随应用附带的示例项目：

- 仓库里放两个示例项目（`crates/mw-project-file/samples/` 下的 `tio2.mwproj`，项目名"TiO₂ 相研究"：金红石和由它派生的 2×2×2 超胞；`perovskite.mwproj`，项目名"钙钛矿氧化物"：SrTiO₃），由 `crates/mw-crystal-io/tests/fixtures/` 里同值的 `rutile.cif`、`SrTiO3.cif` 真实导入、再真实地生成超胞得到，所以示例本身就演示来源记录：带源文件副本和哈希，超胞带派生记录。生成它们的是一个默认忽略的测试（固定时间戳和 UUID，结果可重复）；普通测试检查仓库里的示例项目能打开、内容与重新生成的一致。
- 应用编译时把这些文件嵌进可执行文件（`mw_project_file::samples`，v0.3 有安装包后可以改成放在包里）；`samples::install` 先写到旁边的临时目录再改名，中断不会留下半个项目。仓库的 `.gitattributes` 让 git 不转换其中文件的换行符，否则源文件副本的哈希就对不上了。第一次启动（配置目录里没有 `state.json`）时复制到数据目录并打开；空状态和命令面板的"打开示例项目"同样先复制（已有副本就直接打开）。复制出来的是普通项目，可以编辑和保存。
- `mw_crystal::sample` 不再是模拟：它继续作为单元测试用的参考结构（很多测试用它），文档注释改成这个意思；`rutile.cif` 与它一致的测试已经存在。

## 12. 界面（摘要，详见界面外壳设计稿第 3、4.1、4.4、5、8 节）

- **边栏**：项目列表是当前打开着的项目（启动时恢复上次的）。顶部动作改为 `新建项目…`、`打开项目…`（⇧⌘O）、`打开文件…`（⌘O）、`搜索命令`（⌘K）。打开文件时，结构加入当前项目；没有打开的项目时加入一个新的未命名项目。"导入的文件"项目不再存在。
- **顶栏**：保存状态变成真实的（第 9 节）。
- **快捷键**：⌘S 保存、⇧⌘S 另存为…、⇧⌘O 打开项目…。
- **命令面板**：保存、另存为…、打开项目…、关闭项目、打开示例项目，以及每个最近项目一条"打开最近的项目：名称"。
- **空状态**：没有打开结构时列出最近的项目，外加"打开文件…"和"打开示例项目"。
- **结构的来源**：属性面板末尾的"来源"一节写一行，例如"导入自 rutile.cif"或"由「金红石」生成的 2 × 2 × 2 超胞"，替换了原先超胞诊断的模拟。源文件副本缺失或被改动时，诊断标签页说明这一点。

## 13. 派生结构（M5b）

### 13.1 转为 P1

**决定 6：`ExpandToP1` 在原结构上执行，是一条可以撤销的命令，不生成新结构。**

- 依据：晶体学设计稿 7.1 节（离开对称模式的方式是"`ExpandToP1`（可撤销）"）、7.11 节（转为 P1 后选区和测量通过完整的 ID 映射保留）、7.12 节（逆命令是恢复快照）；界面上现有的文案也是这样写的："转为 P1？……可以撤销"、删除对话框"两种操作都可以撤销"。
- 删除对话框里的"转为 P1 后删除这一个 / 选中的原子"是一步：`Batch [ExpandToP1, RemoveSite…]`，撤销一次回到对称结构。被删的原子按 ID 映射找到转换后对应的位点。
- 撤销栈不存（第 2 节），所以转为 P1 后保存、关闭、再打开，就回不到对称结构了；要回去只能从来源重新导入（源文件副本还在项目里），或 v0.2 的对称化。编辑记录里留着这条命令。
- 实现要点：
  - 新位点按轨道成员展开，坐标是展开时归一化到 [0, 1) 的位置，ID 接在原有 ID 之后；第 k 个成员（从 1 数）的标签是"原标签_k"，轨道只有一个原子时保留原标签；与已有标签冲突时继续加后缀，保证唯一。空间群名称记为 P 1。
  - 各向异性 ADP 随对称操作变换：`U' = N⁻¹·W·N·U·Nᵀ·Wᵀ·N⁻¹`，N = diag(a*, b*, c*)；坐标的 s.u. 按 |W| 传递（不考虑相关性）。
  - 逆命令是恢复整个结构的快照（新增只作逆命令用的 `RestoreStructure`）。
  - ID 映射新增"展开"的去向：旧 `AtomRef(site, k, n)` → 新 `AtomRef(新位点, 0, n)`，选区和测量都换过去而不是失效。

**备选（任务说明里的写法）**：转为 P1 也生成一个新的派生结构，原结构不动。好处是对称结构永远保留，保存后也回得去。代价：边栏里多出副本；"转为 P1 后删除这一个"变成"生成副本、切换过去、在副本里删除"，用户离开了刚才的上下文；测量要复制并换算到新结构；与晶体学设计稿 7.1 节和现有文案不一致，需要一并改。

### 13.2 生成超胞

- `MakeSupercell(M)` 按晶体学设计稿 7.9 节生成新结构：P1，部分占位原样保留，每个占位者的像按出现顺序标为"原标签_n"（Ti1_1 … Ti1_16）；ADP 和 s.u. 同样变换。新结构加进同一个项目、排在来源后面，标为"派生"，并自动打开。来源结构不变、不进撤销栈；新结构的撤销栈是空的。
- 来源记录（第 7.2 节）写明来源和矩阵。测量不带过去：它们引用的是原晶胞里的原子。
- 对话框：三个整数输入框 a、b、c（默认 2、2、2），即 M = diag(a, b, c)；每个 1–20，下面随输入实时写出超胞的原子数，超过 10 万时说明显示会很慢但不禁止。命令和来源记录支持任意整数矩阵（det > 0），一般矩阵的输入界面以后再加。
- 在后台生成，完成后工作区发出 `StructureWorkspaceEvent::MadeSupercell`，外壳把它加进项目（`ProjectCatalog::add_derived`，排在同一来源已有的派生结构之后）并打开；它还没写到磁盘，边栏标出未保存，⌘S 后写入。
- 名字默认"原名 na×nb×nc 超胞"，与已有名字重复时加编号。

### 13.3 能力注册表

`structure.convert_to_p1` 和 `structure.make_supercell` 按 AI 集成设计稿 5.2 节属于 v0.3 的完整 MCP。转为 P1 是一条普通编辑命令，注册它不需要改 `Host`；生成超胞要往项目里加文档，需要给 `Host` 加方法，这会改 `mw-automation` 的公开接口（另一个会话的 `mw-mcp` 在用），所以 M5b 不注册这两个能力，留到 v0.3。

### 13.4 从项目里删除结构

M5b 之后派生结构会越来越多，需要能删除。不在本次范围：删除涉及确认、来源记录里的悬空引用（第 7.2 节已经允许）、打开着的工作区，放到 M6 之后的小改动里。

## 14. 代码放在哪里

| 位置 | 内容 |
|---|---|
| `mw-crystal` | `Structure` 等类型的 serde；`CrystalDocument` 的保存点；`ExpandToP1`、`RestoreStructure`、ID 映射的"展开"；超胞的计算（`transform.rs`） |
| 新 crate `mw-project-file`（纯 Rust） | 清单、结构文件、来源记录、视图状态的类型；读写目录、原子写入、清理、迁移；源文件副本与哈希；示例项目的生成与嵌入 |
| `mw-project` | `ProjectCatalog`：打开着的项目、会话里的 `StructureEntryId` 与条目 ID 的对应、导入或派生后还没写到磁盘的结构和源文件、保存进度（`SaveSnapshot`：写的过程中又有改动时仍是未保存）；边栏 |
| `mw-structure` | `StructureDocument::new` 由结构文件、来源记录和重新解析的数据块构造文档；`StructureWorkspace` 给出要保存的内容（`file_to_save`）、视图状态（`view` / `set_view`，相机经 `Viewport::camera_pose`）并接受外壳告知的项目保存状态；转为 P1、超胞的对话框 |
| `apps/workbench` | 新建 / 打开 / 保存 / 另存为 / 关闭项目的流程（`projects.rs`），最近项目、设置与 `state.json` 的读写（`config.rs`），退出和关窗口时的提示 |

依赖方向：`mw-project-file` 依赖 `mw-crystal` 和 `mw-crystal-io`（重新解析源文件副本）；`mw-project`、`mw-structure` 依赖它。两个能力 crate 仍然互不引用，保存时由外壳从各自取出内容，交给 `mw-project-file` 写出。新增的依赖：`uuid`、`sha2`、`dirs`，都是 MIT / Apache-2.0，已在依赖树里。
