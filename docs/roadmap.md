## 1. 定位与愿景

**Materials Workbench：一个基于 Rust 的现代化、开源、跨平台材料科学桌面工作台。**

以晶体结构的可视化与编辑为起点（对标 VESTA），逐步整合 XRD 衍射分析、CALPHAD 热力学与相图计算、显微组织图像分析，最终形成一个统一的材料科学桌面平台。

**为什么做**：现有材料软件普遍存在三类问题——界面停留在 XP 时代、只有英文、或者把组件堆满屏幕。这些软件的计算能力很强，但用户完成一个任务需要先理解软件内部的概念和菜单层级。我们要做的是在保留专业能力的前提下，让软件围绕材料科学任务组织操作，降低认知负担。

**统一什么、不统一什么**：

- **统一**的是用户体验、项目管理、数据交换和可视化基础设施：一个项目里放结构、衍射谱、相图、显微图像，彼此可以引用。
- **不强行统一**的是算法核心。晶体结构、衍射数据、热力学模型和显微图像的数学模型差异很大，各自是独立的领域引擎（独立 crate，不依赖界面），只共享项目系统、任务调度、可视化和扩展接口。

**AI 原生**：工作台的每个能力都可以被 AI 调用。外部 AI Agent 通过 MCP 操作工作台，应用内置的助手用自然语言分析数据；数值结论始终来自确定性的计算引擎，AI 负责理解意图、编排和解释（第 14 节）。

**对外宣传口径**：每个阶段只宣称已经做好的能力。第一版是"A modern crystallography workspace for materials scientists"，而不是"Materials Studio 的替代品"——后者会让用户期待分子动力学、DFT、聚合物建模等大量不在计划内的功能。

## 2. 目标用户与场景

| 用户 | 典型场景 | 首先需要的能力 |
|---|---|---|
| 材料专业学生 | 课程作业里看懂晶体结构、算键长键角、画晶面 | 打开 CIF、旋转查看、测量、中文界面 |
| 科研人员（计算方向） | 从数据库取结构，建超胞、掺杂、导出给 VASP / Quantum ESPRESSO | 结构编辑、超胞、P1 展开、POSCAR 导出 |
| 科研人员（实验方向） | 把测得的 XRD 谱和候选结构的模拟谱对比、标峰 | XRD 模拟、实验谱导入、寻峰、物相比对 |
| 合金设计 | 查二元相图、算平衡相组成 | CALPHAD 计算、相图绘制 |
| 实验室 / 表征平台 | 金相、SEM 图像的晶粒度与孔隙统计 | 图像分割、颗粒统计、标准方法报告 |

## 3. 竞品与差异化

| 领域 | 主要竞品 | 它们的长处 | 我们的切入点 |
|---|---|---|---|
| 晶体结构 | VESTA、CrystalMaker、Mercury、Diamond、Materials Studio；开源库 ASE、pymatgen、OVITO | VESTA 功能全、免费；CrystalMaker 界面精致（商业、主要在 macOS）；pymatgen 生态强 | 开源、跨平台、中文、项目式工作流、命令面板、严格的对称编辑语义 |
| XRD | Jade、HighScore、GSAS-II、FullProf、TOPAS | 物相库、精修能力成熟 | 与晶体结构模块无缝联动：从结构直接模拟谱并与实验谱对比；现代交互 |
| 热力学 | Thermo-Calc、Pandat、FactSage；开源 pycalphad、OpenCalphad | 工业数据库、多元体系、动力学 | Rust 原生、可嵌入、可复现的计算引擎；先做好二元体系与相图 |
| 显微组织 | ImageJ / Fiji、Dragonfly、Avizo、MIPAR | ImageJ 插件生态庞大；商业软件 3D 能力强 | 面向材料表征任务的流程（标定 → 分割 → 统计 → 按标准出报告），而不是通用图像处理 |

| AI 协作 | 通用 AI 助手（缺少材料领域的计算工具）；部分商业软件开始内置 AI 功能 | 通用模型的语言能力强 | 开放的 MCP 接口：任何 AI Agent 都能调用晶体学、XRD、热力学、显微组织的真实计算；内置助手的每个结论都可追溯 |

不和竞品正面比拼的部分：工业级热力学数据库、Rietveld 精修的全部功能、3D 断层重建、分子动力学与第一性原理计算。

## 5. v0.1 晶体学 Alpha

**范围**以[晶体学数据模型](design/crystallography-model.md)第 10 节的 v0.1 为准。M1–M6 都已实现，下表的验收标准已逐条核对通过（2026-10-23，结果见架构文档第 10 节；POSCAR 用 pymatgen 和 ASE 验证，没有在 VASP 本身上运行）。仍是模拟的部分见架构文档第 9 节，都属于之后的版本。

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| M1 CIF 导入 | CIF 1.1 子集的语法与语义解析（新旧字段别名、s.u. 括号、缺失值、Biso→Uiso、aniso loop（U、B、β））；导入流水线的规范化与诊断（带行号）；"打开文件…"对话框和拖放 | 用 COD 语料批量导入：解析失败率、诊断分布有统计；错误能定位到源文件行 |
| M2 对称性 | 对称操作集（整数矩阵 + 有理平移）、群封闭检查、空间群识别、轨道展开、位点对称性与约束子空间、Wyckoff 指认，真正计算出目前手写的 `Derived` | 230 个空间群的标准 setting 全部通过展开测试；金红石、SrTiO₃ 等示例与手写数据一致 |
| M3 渲染 | 键（impostor 圆柱）、晶胞边框、ID 纹理拾取；在视口里点选原子、测量距离与键角 | 1 万原子 60 fps 不退化（见视口设计稿 8.1 节的基准） |
| M4 基础编辑 | 命令与撤销栈；改晶胞参数（受对称约束联动）、元素、占位率、混合占位，删除位点；P1 模式下自由编辑；建立能力注册表，界面动作改为调用领域命令（第 14 节） | 每个编辑命令都可撤销；对称模式下破坏对称的编辑按设计稿 7.1 节拒绝并给出引导 |
| M5 变换与导出 | 转为 P1、生成超胞（新文档，记录来源）；导出 CIF、POSCAR、扩展 XYZ | CIF 往返测试（导入 → 导出 → 再导入）在 COD 语料上一致；POSCAR 能被 VASP 工具链读取 |
| M6 持久化 | 项目文件（结构、来源记录、视图状态）、最近项目、设置保存 | 关闭再打开项目，状态完整恢复 |

**v0.1 的关键难点**（来自立项讨论，设计稿里有对应方案）：

1. **CIF 不是普通的表格文件**：循环数据、缺失值、数值不确定度、新旧两套字段名都要正确处理。先明确支持的子集，用标准测试文件和 COD 语料验证。
2. **空间群约定繁多**：不能只硬编码 230 个名称。操作集才是事实来源；对称性识别使用纯 Rust 的 moyo，覆盖度已在 M2 验证（见晶体学设计稿第 11 节）。
3. **结构编辑的语义**：编辑原子坐标后如何处理空间群约束、等效原子和部分占位，必须有清晰规则，否则界面看似可用，导出的结构却是错的。

## 6. v0.2 对称编辑

对应晶体学设计稿 v0.2：

- **几何编辑**：拖拽移动位点时把位移投影到约束子空间（原子留在特殊位置上）；按住修饰键可以脱离特殊位置；数值输入按 Wyckoff 表达式联动。已实现（M7，2026-10-23，晶体学设计稿 7.4、7.5 节）。
- **添加位点**：靠近特殊位置时自动吸附；与已有轨道重合时提示改为混合占位。已实现（M7，晶体学设计稿 7.6 节）。
- **对称性检测与对称化**：后台检测，预览空间群、最大位移和是否改变晶胞，确认后再提交。已实现（M9，2026-10-23，晶体学设计稿 7.10 节）：容差可调，可选标准化为标准惯用胞；原子平均到对称位置、等效原子合并为位点，占位率和位移参数一并平均，一步撤销，选区和测量按最近原子跟过去；只读的 `structure.detect_symmetry` 也在 MCP Server 里。
- **晶胞变换**：转原胞、转标准惯用胞、Niggli 约化、换 setting。已实现（M8，2026-10-23，晶体学设计稿 7.8 节）：预设由 moyo 给出，也可以输入任意 (P, p)；原子不动，选区和测量跟着原子走，一步撤销。
- **POSCAR 导入**（含晶格朝向）：已实现（M10，2026-10-23，晶体学设计稿 4.2、9.3 节）。

验收：设计稿第 7 节每一条编辑语义都有对应测试；把 P1 结构对称化后再转回 P1，原子位置在容差内不变。后一条的测试在 `mw-crystal/src/symmetrize.rs`（M9）：全部 530 个表列设定的结构（含转过朝向、左手系、带位移参数的）转为 P1、加上小于容差的扰动、对称化、再转为 P1，原子位置在容差内不变，操作集、标签和位移参数逐项相同。

## 8. v0.4 衍射（XRD）

**目标**：由晶体结构模拟粉末衍射谱，导入实验谱，与模拟谱对比、寻峰、做物相比对。

| 功能 | 内容 | 说明 |
|---|---|---|
| 粉末谱模拟 | 由结构计算结构因子：原子散射因子（Waasmaier–Kirfel 或 Cromer–Mann 参数）、占位率、温度因子；乘以多重度和洛伦兹-偏振因子；峰形用 pseudo-Voigt，支持 Cu Kα₁/Kα₂ 等常用波长 | 直接复用晶体学模块的结构和对称性 |
| 实验谱导入 | 文本格式（`.xy`、`.xye`、CSV）优先，之后支持 PANalytical `.xrdml`、Bruker、Rigaku 等仪器格式，并读取仪器元数据 | 先做开放格式，仪器格式按实验室需求排序（第 13.1、13.4 节） |
| 谱图处理 | 背景扣除、平滑、Kα₂ 剥离、寻峰（位置、强度、半高宽） | — |
| 对比与标定 | 模拟谱与实验谱叠加；峰位对应的 hkl 标注；晶格参数微调后实时更新模拟谱 | 体现与结构模块联动的价值 |
| 物相比对 | 基于开放数据（如 COD）的候选物相检索与匹配打分 | ICDD PDF 是商业数据库，不内置 |
| 全谱拟合 | Le Bail / Pawley 拟合；Rietveld 精修作为更后面的目标 | 结果与 GSAS-II、FullProf 对照验证 |

**验收**：模拟谱的峰位、相对强度与 VESTA、pymatgen 等独立程序对同一结构的结果在容差内一致；寻峰在公开测试数据上有可复现的结果。

**新增 crate**：`mw-diffraction`（计算，无界面）和对应的界面能力 crate。

**内置 AI 助手第一版**同在 v0.4 发布：XRD 物相分析是它的第一个重点场景（"这张谱更像金红石还是锐钛矿"），详见第 14 节。

## 9. v0.5 热力学（CALPHAD）

**目标**：Rust 原生、可嵌入、可复现的 CALPHAD 计算引擎，第一版专注二元合金体系，并在工作台中绘制相图。长期可以成为 Thermo-Calc、Pandat 的开源替代方案之一，但短期不追求覆盖商业软件的全部功能。

### 9.1 第一版算法

1. **热力学模型**：
   - 纯组元参考态 Gibbs 能函数；
   - 二元置换固溶体：G = x_A·G_A⁰ + x_B·G_B⁰ + RT(x_A ln x_A + x_B ln x_B) + G^ex；
   - 超额 Gibbs 能用 Redlich–Kister 展开：G^ex = x_A·x_B·Σ L_k (x_A − x_B)^k；
   - 多个置换固溶相、固定化学计量比化合物。
   - 暂不做复杂亚点阵模型、磁性模型、离子液体模型。
2. **相平衡求解**（两级算法）：
   - 先在成分上离散采样、构造 Gibbs 能下凸包，确定候选稳定相和两相区；
   - 再用 Newton / trust-region 精修平衡成分，检查化学势相等、约束与稳定性。
   - 不能把一个通用非线性优化器直接当成完整的相平衡引擎：共切线方程的解不一定是全局稳定平衡。
3. **二元相图**：温度与成分扫描生成相区，再逐步实现相边界追踪；计算出不变反应。
4. **TDB 子集解析**：`ELEMENT`、`FUNCTION`、`PHASE`、`CONSTITUENT`、`PARAMETER`；不支持的语法明确报错。

### 9.2 开发顺序（参考）

| 阶段 | 内容 |
|---|---|
| 1–2 周 | 理想溶液、正则溶液、Redlich–Kister 模型；解析导数、混合熵、化学势的验证 |
| 3–4 周 | 离散下凸包、两相共切线求解、杠杆定律、相稳定性检查 |
| 5–6 周 | 温度与成分扫描，生成二元相区与相界 |
| 7–8 周 | TDB 子集解析 |
| 9–10 周 | 批量计算、CSV / JSON 导出、Python 绑定、参考测试套件 |
| 11–12 周 | 文档、示例、跨平台 CI、基准测试，发布命令行 Alpha |
| 之后 | 接入工作台：相图交互、平衡计算面板、与 XRD / 显微组织模块联动 |

### 9.3 验收标准

| 测试 | 要求 |
|---|---|
| 理想溶液 | 与解析公式一致 |
| 正则溶液 | 能复现已知的混溶间隙行为 |
| 共切线 | 化学势与截距残差达标 |
| 杠杆定律 | 相分数与总成分守恒 |
| 相稳定性 | 排除局部但非全局稳定的解 |
| 参考相图 | 与 pycalphad 在相同模型输入下比较 |
| 异常处理 | 不收敛、参数非法、超出支持范围时明确报错 |

数值容差按物理量尺度、模型条件数和参考解精度分别制定，不统一套用一个阈值（简单无量纲模型可以先以 10⁻⁸ 量级的残差为目标之一）。

### 9.4 数据授权

能解析某种数据库格式，不代表可以分发该数据库。商业热力学数据库不内置；项目自带的数据只使用明确允许再分发的公开数据库，或自己构造的测试数据。每个内置数据集都要记录来源与许可。

### 9.5 crate 规划

计算核心拆成可以独立发布的 crate，方便在 Rust / C++ 程序和 Python 中嵌入：

- `mw-thermo`：Gibbs 能模型与热力学函数；
- `mw-tdb`：TDB 解析；
- `mw-equilibrium`：相平衡求解；
- `mw-phase-diagram`：相图计算。

技术选型：数值线性代数用 nalgebra，并行用 Rayon，解析器用 winnow 或 chumsky，基准测试用 Criterion，性质测试用 proptest。第一版不需要 GPU：对二元体系来说，求解器的稳定性和模型正确性比 GPU 加速重要得多。

**后续扩展**：多元体系、亚点阵（化合物能量）模型、磁性贡献、Scheil 凝固模拟、扩散动力学。

## 10. v0.6 显微组织

**目标**：金相与 SEM 图像的定量分析，面向材料表征任务，而不是通用图像处理。

| 功能 | 内容 |
|---|---|
| 图像导入 | TIFF（含 16 位）、PNG、JPEG、Gatan `.dm3` / `.dm4`；读取常见电镜厂商写在文件里的像素尺寸等元数据（第 13.1 节） |
| 标定 | 按元数据或比例尺标定像素尺寸 |
| 预处理 | 去噪、背景校正、对比度调整 |
| 分割 | 全局 / 自适应阈值（如 Otsu）、分水岭分割粘连颗粒；人工修正 |
| 统计 | 颗粒尺寸分布、面积分数、长径比、圆度；孔隙率；第二相分数 |
| 晶粒度 | 按 ASTM E112 / ISO 643 的截线法与面积法 |
| 报告 | 导出统计表与带标注的图像；记录完整处理参数以便复现 |
| 之后 | EBSD 数据（`.ang`、`.ctf`）的取向成像与晶粒重构，与晶体学模块共享对称性 |

**验收**：在公开测试图像上，统计结果与 ImageJ / Fiji 用同样参数得到的结果一致；晶粒度测量与标准试样的标称值一致。

## 13. 仪器与实验室数据对接

"对接仪器"分三层，由浅入深。越往深，越依赖厂商的私有协议、授权和安全要求，所以前两层自己做，第三层只提供扩展框架。

| 层 | 内容 | 时间 |
|---|---|---|
| 第一层 | 读取仪器导出的数据文件和元数据 | 随 v0.4（XRD）、v0.6（显微组织）实现，其他谱学按需求加入 |
| 第二层 | 自动导入与批处理：实验室数据管线 | v1.0 之后，依赖项目系统和后台任务 |
| 第三层 | 仪器控制与采集：只提供插件框架，不自己写驱动 | 依托 v1.0 的扩展接口 |

### 13.1 第一层：读取仪器导出的数据文件

投入产出比最高。常见格式与对应版本：

| 仪器 | 常见格式 | 版本 |
|---|---|---|
| XRD | 通用 `.xy` / `.xye` / CSV；PANalytical `.xrdml`（XML）；Bruker `.brml`（压缩包内为 XML）/ `.raw`（二进制）；Rigaku `.ras` / `.rasx` | v0.4 |
| SEM / TEM 图像 | 带厂商元数据的 TIFF（Thermo Fisher / FEI、Zeiss、JEOL、Hitachi 等）；Gatan `.dm3` / `.dm4` | v0.6 |
| EBSD | EDAX `.ang`；Oxford `.ctf` / `.h5oina` | v0.6 之后 |
| EDS 能谱 | EMSA / MSA 标准格式；Bruker `.spx` | 按需求 |
| 拉曼、红外等光谱 | JCAMP-DX、SPC | 按需求 |
| DSC、TGA 等热分析 | 通常只能导出 CSV 或文本 | 按需求 |
| 同步辐射、中子 | NeXus / HDF5 | 按需求 |

**共同要求**：

- **一种格式一个适配器**，输出所属模块的数据类型（衍射谱、图像、能谱等），外加一份统一的仪器元数据。适配器放在所属模块的 IO crate 里，元数据类型放在共享 crate 里。
- **元数据进入项目的来源记录**：仪器型号、控制软件版本、测量时间、样品名，以及与数据相关的参数（波长、步长、扫描速度、加速电压、工作距离、像素尺寸等），以便复现和追溯。
- **解析要宽容**：缺字段时给出诊断，而不是整个文件导入失败。不同型号、不同软件版本写入的元数据差别很大，要用真实文件覆盖这些差异。
- **私有二进制格式**优先按公开文档或厂商的开放导出功能来实现。
- **测试数据**：每种格式至少有一份真实仪器文件作为测试数据。这需要实验室提供；提交进仓库前要确认可以公开，并去掉敏感信息。

### 13.2 第二层：自动导入与批处理（实验室数据管线）

不碰仪器本身，风险低，对实验室的实际价值很大。

- **监听文件夹**：监听仪器电脑的导出目录或网络共享盘。新文件按规则导入指定项目，规则按路径或文件名模式决定项目、样品名和数据类型。
- **预设处理流程**：导入后自动执行。例如：
  - XRD：扣背景 → 寻峰 → 物相比对；
  - SEM：标定 → 分割 → 统计。
  - 结果和使用的参数一起记录。
- **批量重算**：修改流程参数后，对整批数据重新计算，并保留每次计算的版本。
- **导出与对接**：生成带完整来源记录的报告；对接电子实验记录本（例如开源的 eLabFTW）和数据仓库。
- **可靠性**：
  - 原始文件只读，绝不修改；
  - 按内容哈希识别重复文件；
  - 共享盘或网络不可用时自动重试，不丢数据；
  - 每次导入和处理都有日志。

**验收**：在模拟"仪器电脑"的目录里连续投放文件，导入、处理和结果都能复现；中途断开共享盘再恢复，不丢文件、不重复导入。

### 13.3 第三层：仪器控制与采集（只提供扩展框架）

- **不自己编写各厂商仪器的驱动**。XRD、SEM、TEM 等表征仪器由厂商软件控制，协议私有，还涉及安全和资质。
- **由用户或厂商编写适配插件**，依托 v1.0 的扩展接口（Python 插件、进程间 API）：
  - 有脚本接口的仪器：例如 Thermo Fisher 电镜的 AutoScript（Python）；
  - 通用实验设备（温控器、电源、炉子等）：SCPI / VISA 等标准协议；
  - 同步辐射和中子源：EPICS、Bluesky。这类设施的数据通常已经是 NeXus / HDF5，主要在第一层支持读取。
- **框架提供**：设备连接状态、采集任务与进度、采集结果作为数据对象进入项目、完整的操作日志。
- **安全要求**：
  - 插件默认只读，只采集数据；
  - 任何会改变仪器状态的操作都必须由用户明确确认；
  - 插件运行在独立进程里，崩溃不影响主程序。

### 13.4 优先级

先支持哪些格式，按实验室实际在用的仪器排序：需要仪器的品牌、型号，以及几份样例文件。拿到清单之前的默认顺序：

1. 通用文本格式（`.xy`、CSV）
2. PANalytical、Bruker、Rigaku 的 XRD 格式
3. 电镜 TIFF 元数据
4. EBSD
5. EDS
6. 其他谱学数据

## 14. AI 集成（MCP 与内置助手）

详细设计见 [AI 集成设计稿](design/ai-integration.md)。两个方向共用一套底层能力：

- **MCP Server**：Claude Desktop、Claude Code 等外部 AI Agent 可以打开项目、查询结构、执行编辑和计算、导出结果。连接运行中的应用时，操作在界面里实时可见、可以撤销；也可以无界面运行，用于批处理。
- **内置助手**：右侧面板的"助手"标签，理解当前项目和选中对象，用自然语言分析数据，在用户确认下执行操作。默认使用 Claude，也支持其他模型服务和本地模型。

**核心原则**：

- 一套能力，多个入口。GUI、命令面板、Python、命令行、MCP、助手调用的都是能力注册表（`mw-automation`）里的同一批领域命令和查询。
- 数值结论只来自确定性的计算引擎，每个结论都能追溯到一次工具调用。
- AI 的写操作进入同一个撤销栈；不可逆、外发、改变仪器状态的操作必须由用户确认；全部写入审计日志。
- 文件内容是数据不是指令，防止提示注入。

| 版本 | 内容 |
|---|---|
| v0.1（随 M4） | 能力注册表的基本结构；领域命令可序列化，界面动作改为调用领域命令 |
| v0.2 | 实验性 MCP Server：只读工具、导出 CIF / POSCAR 文本、结构资源 |
| v0.3 | 完整 MCP：编辑与写文件、视图工具与视口截图、权限设置、审计日志；与 Python、命令行一同发布。MCP、Python 和命令行都已实现（M18、M19，2026-10-24），还没发布 |
| v0.4 | 内置助手第一版：工具调用卡片、确认交互、会话撤销；首个重点场景是 XRD 物相分析与结构问答 |
| v0.5 起 | 每个新模块发布时一并提供它的能力与评测任务 |
| v1.x | 挂载外部 MCP Server、本地模型、实验室数据管线的能力、仪器插件 |

**验收**：在 Claude Code 里完成"打开项目 → 总结结构 → 生成超胞 → 导出 POSCAR"，界面实时可见、可以撤销、审计完整；一组固定的评测任务用于跟踪工具调用成功率，每次修改能力说明后重跑。

## 16. 开源与发布策略

- **许可证**：MIT OR Apache-2.0 双许可，与 Rust 生态的惯例一致（仓库根目录的 `LICENSE-MIT`、`LICENSE-APACHE`；工作区 `Cargo.toml` 的 `license` 字段由各 crate 继承）。
  - 贡献默认按同样的双许可授权，见 README。
  - 依赖只引入与双许可兼容的许可证：2026-10-22 核对时，全部依赖都是 MIT、Apache-2.0、BSD、ISC、Zlib、Unicode-3.0 等宽松许可，以及少量文件级的 MPL-2.0。引入新依赖时同样检查，不引入 GPL 类许可的依赖，也不复制 GPL 代码。
  - 依赖的许可由 `deny.toml` 和 cargo-deny 检查，CI 每次运行（2026-10-24 起）。
  - 安装包附带第三方许可清单，在 v0.3 打包时用 cargo-about 生成（发布与打包设计稿第 7 节）。
  - 内置数据（元素数据、晶体结构、热力学数据库等）单独记录许可。
- **早公开**：不等界面完成才发布。每个模块都先让计算核心可用、可验证，再接入界面。
- **独立 crate**：领域 crate 单独发布到 crates.io（晶体学、XRD、热力学各自成套），比把全部功能封装在一个界面里更容易获得科学计算开发者的关注。
- **可复现**：公开模型输入、计算结果、参考数据和复现命令；关键结论用解析解、文献或独立程序验证。
- **展示**：每个模块都准备一个"从输入到结果"的完整示例作为主页演示，例如热力学模块的"从 Gibbs 自由能曲线到二元相图"。

## 17. 开发方式

- 用 AI 当两个职责不同的协作者，而不是让两个模型轮流写同一份代码：一个负责实现，另一个独立审查数学假设和测试覆盖。
- 物理结论不能只靠 AI：必须用解析解、文献数据或独立程序（pymatgen、VESTA、pycalphad、GSAS-II、ImageJ 等）核对。
- 每个功能按开发指南第 5 节的流程交付：先改设计稿，再在不依赖界面的 crate 里实现并测试，最后接入界面、替换模拟、更新文档。

## 18. 风险与未决问题

| 项 | 影响 | 应对 |
|---|---|---|
| GPUI 生态较年轻，API 仍在变化 | 升级 GPUI Kit 时可能需要改动界面代码 | 只依赖 `gpui-kit` 一个入口；升级时按视口设计稿附录复核 |
| 对称性库的选择（moyo / spglib） | 影响 M2 的工作量和跨平台构建 | 已在 M2 验证并选用 moyo；它仍是 0.x，锁定小版本，调用集中在 `mw-crystal/src/tables.rs` |
| 物相与热力学数据的授权 | 决定能内置什么数据 | 只内置明确允许再分发的数据，并记录来源 |
| Linux / Windows 视口性能未测 | 可能需要零拷贝方案 C | v0.3 发布前重测，按视口设计稿第 6 节逐平台处理 |
| 个人开发、范围很大 | 进度不可控 | 每个版本只做一个领域；每个里程碑都能单独交付 |
| 依赖或参考代码的许可不兼容 | 无法按双许可发布 | 引入依赖时检查许可；GPL 类代码只参考设计、不复制；打包时生成第三方许可清单 |
| AI 在科学问题上出错 | 错误结论误导用户 | 数值只来自引擎；结论必须引用工具结果；评测集包含科学正确性检查 |
| 提示注入与数据外泄 | AI 被文件中的指令诱导越权操作 | 文件内容标记为不可信；权限在能力注册表强制执行，高风险操作必须确认 |
| 缺少真实仪器文件 | 仪器格式无法验证，元数据差异覆盖不全 | 向实验室收集样例文件，确认可公开后再进仓库 |
| 仪器私有格式与协议 | 格式变化、授权限制；控制仪器有安全风险 | 优先公开文档和厂商开放导出；仪器控制只做插件框架，默认只读 |
