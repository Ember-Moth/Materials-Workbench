# 3D 视口：技术选型与 GPUI 集成

> 状态：已决定 · macOS 上已用 PoC 验证方案 A（见 8.1 节），Linux / Windows 待测 · M3 已实现键、晶胞边框、ID 纹理拾取和测量（5.4–5.6 节、8.2 节）· 2026-10-22；2026-10-23 补充上游现状和不改 GPUI 的零拷贝路线（方案 F，3.5、6.1–6.3 节），方案 F 的可行性见[可行性报告](viewport-underlay-feasibility.md)；同日在方案 A 内减少往返：一轮改动只出一帧、交互时降分辨率、悬停圈改为二维叠加、跳过过时帧的拷贝、标注按屏幕上那一帧投影（5.3–5.6 节、8.3 节）；2026-10-24 M14 的大显示范围在后台计算，计算耗时见 8.5 节（屏幕上的帧率待补测）；同日 M15 加了半透明多面体，按深度排序（5.6 节），耗时见 8.6 节
> 相关：[晶体学模块：数据模型与编辑语义](crystallography-model.md)（显示范围等视图状态，以及拾取结果如何映射到 `AtomRef`）
> 源码结论基于 GPUI Kit 0.8.0 锁定的 `gpui-pre 0.3.9` 系列 crate，于 2026-10-22 从 crates.io 下载后逐一核对。升级 GPUI Kit 时，按附录清单重新核对。

## 1. 决定

| 项 | 决定 |
|---|---|
| UI 框架 | GPUI，通过 GPUI Kit 使用（应用只依赖 `gpui-kit` 一个 crate） |
| 3D 渲染 | wgpu，版本与 GPUI 的 wgpu 渲染器对齐（当前为 29.x） |
| 渲染器边界 | `mw-crystal-render` 只依赖 wgpu，不依赖 GPUI |
| 视口接入 GPUI | 第一阶段：离屏渲染 → 回读到内存 → `Window::paint_image`，全平台通用（方案 A）。只有实测证明回读不够用时才做零拷贝：优先等上游接受外部纹理图元（方案 C）；进不了上游时，用不改 GPUI 的底层合成（方案 F，6.2 节） |
| 原生子视图 | 不采用 |
| Bevy | 不采用 |

## 2. 约束

视口不是一块孤立的画布，它必须和工作台的其余部分融为一体：

- **GPUI 弹层必须能盖在视口上**：命令面板、右键菜单、悬停提示（原子信息）、测量标注、对话框。
- **文字由 GPUI 绘制**：原子标签和测量值要和界面使用相同的字体、支持中文、跟随主题色。
- **平台与显示**：macOS、Windows、Linux 三个平台都要支持；HiDPI 下像素精确，不发虚。
- **按需渲染**：画面不变时，GPU 和 CPU 占用接近 0。
- **Web**：将来可能做网页版查看器（GPUI Kit 有 WebAssembly 目标）。

## 3. 源码核查结论

### 3.1 各平台的 GPUI 渲染器

`gpui-pre-platform 0.3.9` 的 `Cargo.toml` 按目标平台选择后端：

| 平台 | 后端依赖 | 图形 API |
|---|---|---|
| macOS | `gpui_macos` → `gpui_apple::metal_renderer` | Metal |
| Linux | `gpui_linux` + `gpui_wgpu`（包名 `gpui-pre-wgpu`） | wgpu 29（Vulkan 等） |
| Windows | `gpui_windows`（包名 `gpui-pre-windows`） | Direct3D 11 + DirectComposition |
| Web | `gpui_web` | wgpu（优先 WebGPU，失败时退回 WebGL2） |

### 3.2 外部 GPU 画面能否直接显示

GPUI 有一个 `Surface` 图元，但它是为通话视频设计的：

| 位置 | 结论 |
|---|---|
| `gpui-pre`：`src/elements/surface.rs:35` 的 `surface()`，`src/window.rs:5155` 的 `Window::paint_surface` | 都带 `#[cfg(any(target_os = "macos", target_os = "ios"))]`，其他平台没有这个 API |
| `gpui-pre`：`src/scene.rs:768` 的 `PaintSurface` | 内容字段是 `CVPixelBuffer`，同样只在 macOS / iOS 上存在 |
| `gpui-pre-apple`：`src/metal_renderer.rs:1219-1221` | 断言像素格式必须是 `kCVPixelFormatType_420YpCbCr8BiPlanarFullRange`（YUV 4:2:0 双平面）。1245-1246 行分别把 Y 平面按 `R8Unorm`、CbCr 平面按 `RG8Unorm` 采样 |
| `gpui-pre-wgpu`：`src/wgpu_renderer.rs:1614` | 绘制分支为 `PrimitiveBatch::Surfaces(_surfaces) => {}`，旁边的注释说明 Surface 只用于 macOS 视频播放，wgpu 渲染器没有实现。不过 surfaces 管线和绑定布局已经创建（第 136、163、567、920 行） |
| `gpui-pre-windows`：`src/directx_renderer.rs:816` | `draw_surfaces` 是空实现 |

**结论：现有 GPUI 在任何平台上都不能零拷贝显示外部渲染的 RGB 画面。** macOS 的 Surface 只接受 YUV 4:2:0；把 3D 画面转成 YUV，细键、边缘和文字会出现色彩失真，不可接受。

### 3.3 可用的通用接口

| 位置 | 用途 |
|---|---|
| `gpui-pre`：`src/window.rs:5053` 的 `Window::paint_image` | 绘制一张 `Arc<RenderImage>`，全平台可用 |
| `gpui-pre`：`src/window.rs:5175` 的 `Window::drop_image` | 把图像从精灵图集中移除。每帧换新图时必须调用，否则图集会持续增长 |
| `gpui-pre`：`src/assets.rs:42-43` 的 `RenderImage` | 文档注释写明数据是 BGRA 格式 |
| `gpui-pre`：`src/window.rs:6926` 的 `Window::gpu_specs`，返回 `src/gpui.rs:393` 的 `GpuSpecs` | 提供 GPUI 所用 GPU 的 `device_name` 和 `driver_name`，可以用来让 wgpu 选同一块 GPU |
| `gpui-pre-wgpu`：`src/wgpu_context.rs:14-15` | `WgpuContext` 有 `pub device` 和 `pub queue`，但没有通过 `Window` 暴露给应用 |

### 3.4 GPUI Kit 文档中的相关限制

- **原生子视图**（`docs/native-extension.md`，即 `gpui-webview` 的实现方式）：
  - 子视图位于 GPUI 内容之上，GPUI 的弹出层、对话框和提示无法可靠地盖住它。
  - Windows 上要在启动前设置 `GPUI_DISABLE_DIRECT_COMPOSITION=true`。
  - Linux 上只有 X11 / XWayland 有可行路径。
- **渲染测试**（`docs/test.md`）：GPUI Kit 的像素级渲染测试覆盖 macOS（Metal）和 Linux（WGPU）；Windows 没有无头渲染器。
- **WebAssembly**（`docs/webassembly.md`）：只有一个 canvas、一个顶层窗口；WebGPU 失败时退回 WebGL2。

### 3.5 底层合成可用的接口（2026-10-23 核对）

方案 F（6.2 节）不改 GPUI，只依赖下面这些已有的接口：

| 位置 | 结论 |
|---|---|
| `gpui-pre`：`src/platform.rs:2766` 的 `WindowBackgroundAppearance` | 窗口可以用透明背景 |
| `gpui-pre-apple`：`src/metal_renderer.rs:182`、`484` | 透明背景时，GPUI 的 Metal 图层设为非不透明（`set_opaque(!transparent)`），下面的内容能透上来 |
| `gpui-pre`：`src/window.rs:7572` | `Window` 实现了 `HasWindowHandle`，可以拿到原生窗口（NSView、HWND、Wayland 表面） |
| `gpui-pre-windows`：`src/directx_renderer.rs:1017` | GPUI 用 `CreateTargetForHwnd(hwnd, true)` 建的是"顶层"DirectComposition 目标。每个窗口还可以有一个非顶层目标，系统把它合成在顶层目标下面 |
| `gpui-pre-macos`：`src/window.rs` 1087–1089、1192–1200 | GPUI 的 `GPUIView` 只是窗口内容视图的一个普通子视图；GPUI 自己插模糊背景视图时，也是放进内容视图的最底层（1886–1899） |
| `wgpu-29.0.4`：`src/api/surface.rs:392`、`400` | `SurfaceTargetUnsafe::CoreAnimationLayer` 和 `SurfaceTargetUnsafe::CompositionVisual`：wgpu 能直接在 Core Animation 图层和 DirectComposition 视觉对象上创建绘制目标。后者只有 DX12 后端支持 |

## 4. 方案比较

| 方案 | 做法 | 弹层能否盖住视口 | 平台 | 主要代价 | 结论 |
|---|---|---|---|---|---|
| A 回读 | wgpu 离屏渲染 → 拷到 CPU → `paint_image` | 能 | 全部 | 每帧一次 GPU→CPU→GPU 往返 | **第一阶段采用** |
| B 原生子视图 | 在 GPUI 窗口中嵌入原生 view，wgpu 直接画在上面 | 不能 | macOS、Windows、Linux X11 | 弹层被挡；Wayland 不可用；Windows 要关闭 DirectComposition | 不采用 |
| C 打补丁零拷贝 | 给 GPUI 加一个"外部纹理"图元 | 能 | 逐个平台实现 | 需要维护 `gpui-pre` 补丁 | **视实测结果，第二阶段采用** |
| D GPUI 原生绘制 | 用 `paint_path` 和图片精灵画 2.5D 球棍模型，在 CPU 上按深度排序 | 能 | 全部 | 没有真实深度，相交处画错，大结构性能差 | 不作为主视口，可用于缩略图 |
| E Bevy | 用 Bevy 渲染 | 同方案 A / C | — | 见第 7 节 | 不采用 |
| F 底层合成 | wgpu 直接画在一个原生子图层上，这个图层放在 GPUI 内容的**下面**；GPUI 窗口用透明背景，只在视口处留洞，由系统合成器把两层叠起来 | 能 | Windows、Linux Wayland、macOS（较脆弱）；X11 不可用 | 每个平台要写一层图层胶水（unsafe）；两层要同步提交；整个窗口变透明；截图和测试拍不到 3D 画面 | **备选，现在不采用**：macOS 原型可行但有风险，Windows、Wayland 只在源码上可行（6.2 节、[可行性报告](viewport-underlay-feasibility.md)） |

**方案 A 的带宽估算**：每帧字节数 = 宽 × 高 × 4。

| 视口物理像素 | 每帧数据量 | 60 fps 时的单向带宽 |
|---|---|---|
| 1280 × 800 | 约 4 MB | 约 0.25 GB/s |
| 2560 × 1600 | 约 16 MB | 约 1 GB/s |
| 3840 × 2160 | 约 33 MB | 约 2 GB/s |

每帧回读、上传各要走一次。缓解手段见 5.3 节，实际开销以 PoC 实测为准。

## 5. 选定架构

### 5.1 crate 边界

```text
mw-crystal          结构模型与派生数据（见晶体学设计稿）
   │
mw-crystal-render   只依赖 wgpu：场景构建、渲染管线、拾取、相机
   │                输入：wgpu Device / Queue + 结构快照 + 相机 + 视图状态
   │                输出：颜色纹理 + 拾取 ID 纹理（+ 深度）
   │
apps/desktop        视口呈现层
   ├── 回读呈现       方案 A，全平台
   └── 共享纹理呈现   方案 C，按平台逐个加入
```

- **渲染器完全不知道 GPUI 的存在**，可以无头运行：渲染到纹理，再与参考图比对，作为渲染回归测试。这条路不依赖 GPUI 的无头渲染器，所以 Windows 上也能跑。CI 上用软件适配器跑渲染器测试和界面集成测试（Linux 用 lavapipe，Windows 用 WARP；M13，开发指南 2.1 节）。
- **呈现层只负责"把一张纹理放进 GPUI 布局"**。在方案 A 和 C 之间切换，不影响渲染器。

### 5.2 设备与适配器

- 方案 A 下，渲染器自己创建 wgpu 的 Instance、Adapter 和 Device。
- **适配器选择**：用 `Window::gpu_specs()` 返回的 `device_name` 去匹配 wgpu 的适配器信息，尽量和 GPUI 用同一块 GPU，因为双显卡笔记本上跨卡拷贝更慢。匹配不上时，退回 `HighPerformance` 偏好。
- **环境变量**：渲染器读 wgpu 的实例变量（`WGPU_BACKEND` 等）和 `WGPU_ADAPTER_NAME`（适配器名字里含这段文字，不分大小写），设了时只在这些适配器里选，没有就报错并列出所有适配器。CI 用它们固定到软件适配器；驱动有问题时也可以手动换后端。GPUI 自己的渲染器不读这些变量。
- **wgpu 版本锁定**为和 `gpui-pre-wgpu` 相同的大版本（当前是 29）。这样依赖树里只有一份 wgpu；这也是方案 C 在 Linux / Web 上共用设备的前提。

### 5.3 方案 A 的帧流程

1. **只在需要时渲染，一轮改动只出一帧**：场景、选中圈和相机的改动只把视口标记为"需要重绘"，在这一轮更新结束时（`cx.defer`）统一提交一帧；布局尺寸和主题色的变化在 prepaint 时提交。画面没有变化就不渲染。
   - 编辑会先换场景（清掉选中圈）、再恢复选中圈，以前连续提交两帧，现在合成一帧。
   - 不等到 prepaint 再提交：GPUI 跟着显示刷新绘制，改动要等下一次 prepaint 才提交，就要多等一个刷新周期才上屏。
2. **离屏渲染**：渲染器渲染到离屏纹理（MSAA 解析之后）。拾取 ID 纹理不随每帧渲染，只在拾取时按需重画（见 5.4 节）。
3. **拷贝到暂存缓冲**：用 `copy_texture_to_buffer`。每行的字节数要按 wgpu 的 256 字节对齐（`COPY_BYTES_PER_ROW_ALIGNMENT`）补齐，读出时再去掉补齐的部分；宽度是 64 像素的倍数时没有补齐，整块一次拷贝。
4. **异步映射**：`map_async` 映射缓冲，**绝不在 UI 线程上阻塞等待**。暂存缓冲准备几个轮流使用，不同尺寸的可以并存。
5. **过时帧不拷贝**：映射完成后，后台线程先看渲染器是否已经提交了更新的帧，有就直接归还缓冲、不拷贝（`PendingFrame::wait_latest`）。同一队列上的帧按提交顺序完成，更新的那帧随后就到，这一帧拷出来也会马上被替换。
6. **交给 GPUI**：映射完成后构造 BGRA 格式的 `RenderImage`，通知视图重绘。在 paint 阶段调用 `paint_image`，同时对上一帧的图像调用 `drop_image`。
7. **只显示较新的帧**：`mw-viewport` 最多允许两帧在途，它们各自在后台执行器上等待映射，回到 UI 线程的顺序没有保证。帧按提交顺序编号，比屏幕上那一帧旧的直接丢弃。
   - 编辑曾经连续提交两帧，旧帧后完成时覆盖掉带描边的新帧，看起来像是描边消失了。现在编辑只出一帧，但连续拖动时仍会有两帧在途，所以编号检查保留。
   - `Viewport::is_current` 报告屏幕上是不是最后提交的那一帧、且没有帧在途、也不在交互降分辨率期间。界面集成测试用它检查这一点，并用多个随机种子让测试调度器以不同顺序完成两帧。
8. **浮层按屏幕上那一帧定位**：每一帧记住渲染时的相机和场景中心，`Viewport::project` 用屏幕上那一帧的，而不是当前相机。快速旋转时屏幕上的画面比相机晚一两帧，以前测量标签会因此漂开约 20 px（3 rad/s 时）；现在标签只在新画面到达时才和它一起移动。

**分辨率策略**（`mw-viewport` 已实现）：

- 拖动旋转和滚轮缩放期间按 0.5 倍渲染（每个方向，像素数为四分之一），由 GPUI 拉伸显示。线宽和圈宽按同样的比例换算，拉伸后宽度不变。
- 相机最后一次移动约 150 ms 后，补渲染一帧全分辨率画面；按住鼠标但不动也算停下。
- 渲染器为最近用过的两种尺寸各留一套渲染目标，全分辨率和交互分辨率来回切换时不用重新分配。代价是多占一套半尺寸的目标：视口 1792×1600 时全尺寸一套约 103 MB（4× MSAA 颜色和深度各约 46 MB、解析纹理 11.5 MB），半尺寸一套约 26 MB。
- 拾取的 ID 纹理始终按全分辨率画，与屏幕上是哪种分辨率无关。
- 静止的画面不再重绘。

### 5.4 拾取

- 拾取与呈现方式无关。渲染器维护一张 `R32Uint` 格式的 ID 纹理，点击或悬停时只回读鼠标周围一个 9 × 9 像素的小区域，取离鼠标最近的对象，这样细键和原子的柔边也容易点中。
- **ID 纹理单独用 1× 采样渲染，不作为主画面的附加附件。** 同一个渲染通道的所有附件必须采样数相同，而主画面是 MSAA 4×：WebGPU 不保证 `R32Uint` 支持多重采样（wgpu-types 的 `guaranteed_format_features` 里它没有 MSAA 标志），整数格式也不能解析（resolve），所以无法和颜色一起画在一个通道里。单独一个 1× 通道还有两个好处：每个像素恰好一个 ID，不必从多个样本里挑；不拾取时完全不花这份开销。
- **按需重画、跨帧复用。** 渲染器记住 ID 纹理对应的相机、尺寸和场景版本（`set_scene` 时加一）。拾取请求的相机或场景变了才先重画 ID 通道，否则只拷贝那 9 × 9 个像素，所以在静止的画面上移动鼠标几乎不占 GPU。高亮圈和线段不参与拾取，改变它们不会使 ID 纹理失效。
- **ID 编码**：高 2 位是类别（1 = 球，2 = 键），低 30 位是该类别在当前场景里的实例下标，0 表示背景。渲染器只返回 `Pick::Sphere(i)` / `Pick::Bond(i)`，不知道原子是什么；`mw-structure` 构造场景时让第 i 个球对应显示范围里的第 i 个显示原子（晶体学设计稿 5.5 节；多面体模型下补画的配体接在后面），由它映射到 `AtomRef`（位点、轨道成员、晶胞偏移）。多面体不画进 ID 纹理（5.6 节），点击穿过它。以后键、晶胞边、多面体要能选中时，加类别即可。
- **异步与合并**：拾取和出帧一样在后台执行器上等待映射。`mw-viewport` 同一时刻只有一个拾取在途：点击按顺序排队，悬停只保留最新的鼠标位置；拖动旋转期间不做悬停拾取。悬停结果晚一两帧到达是可以接受的（实测见 8.2 节）。
- **悬停不出帧**：悬停的对象变了，只重画叠在画面上的悬停圈（5.5 节）和鼠标指针，不重新渲染 3D、不回读。
- **浮层不能漏点**：视口上的工具条用 `occlude()` 挡住鼠标，点它的按钮不会穿透到原子；标签和提示框不接收鼠标，点在它们上面等于点在下面的原子上。

### 5.5 文字与标注

原子标签、测量数值和坐标轴标签都由 GPUI 画在视口之上：

1. 渲染器提供相机矩阵。
2. 呈现层把 3D 锚点投影到视口坐标。
3. GPUI 的文本系统在这些坐标上绘制文字。

这样字体、中文和主题色都与界面一致，HiDPI 下也清晰。第 2 步用的是屏幕上那一帧渲染时的相机（5.3 节第 8 条），所以标注始终贴着画面，相机转动时和画面一起晚一两帧移动。标签被原子遮住时，根据拾取 ID 纹理或深度判断是否隐藏（尚未实现，目前标签总是显示）。

M3 里已经这样画的有：

- **测量标签**：距离标在两原子中点上方，键角标在顶点处、两臂在屏幕上的角平分线方向内侧约 40 px，避免和两条边上的距离标签挤在一起。
- **悬停提示**：鼠标下的原子旁边显示位点标签和这个原子的分数坐标（含晶胞偏移），测量时可以确认点的是哪一个像。提示框放在原子右上方，不接收鼠标，所以不会挡住拾取、引起闪烁。
- **悬停圈**：`mw-viewport` 在画面上面画一个圆环（`paint_quad`，圆角等于半径，只画边框），圆心和半径由屏幕上那一帧的相机投影得到，宽度和颜色与原来 3D 里画的一致（选中色和背景色在线性空间里各取一半）。悬停的原子是拾取命中的，一定可见，所以不需要深度：唯一的差别是离相机更近的原子盖住它的边缘时，圆环画在那个原子上面。悬停的原子已被选中时不画，由 3D 里的选中圈表示。
- **测量提示**：测量模式下视口顶部居中显示下一步该点什么。

### 5.6 渲染技术（第一版）

渲染器的输入是一个 `Scene`（球、键、线段三种实例和半透明的多面体）加上单独设置的高亮圈。着色器共用 `common.wgsl`（相机、拾取 ID、深度与光照函数），拼在各自的源码前面编译。

- **原子**：impostor 球——画一个面向屏幕的四边形，在片元着色器里做光线求交并写入正确的深度，用一次实例化绘制完成。四边形只比球大出 0.75 个像素，刚好容下轮廓外半个像素宽的覆盖率过渡带；原子只有几个像素大时，留得再多就会成倍增加片元数（8.2 节）。
- **键**：impostor 圆柱，同样写入正确的深度。四边形沿投影后的轴线铺开、两端各外扩一个半径；片元着色器解视线与无限圆柱的二次方程，取靠近相机的交点，轴向参数落在两端之外就丢弃。两端不封口：端点在原子中心，被原子挡住。轴向参数小于一半用起点原子的颜色，否则用终点原子的颜色。正交投影下圆柱侧面的投影是一条半宽恰为半径的带子，所以覆盖率按片元到投影轴线的距离算，和球一样走 alpha-to-coverage。
- **晶胞边框**：线段画成屏幕空间的四边形，宽度按逻辑像素给、乘以缩放比（wgpu 的 `LineList` 只有 1 物理像素宽，HiDPI 下太细），两端各延长半个线宽，让晶胞的角闭合。线段参与深度测试，被原子正确遮挡。线段也可以画成虚线（测量线）。
- **高亮圈**：选中的原子在轮廓外画一圈环，宽度按逻辑像素给。环的深度取原子离相机最近那一点的深度：键和后面的东西不会切断它，更近的原子仍会挡住它。环最后画，不写深度。改变高亮只上传几个实例，不重建场景。被挡住的原子也可能被选中，所以选中圈留在 3D 里；悬停圈改为叠在画面上（5.5 节）。
- **晶格平面**：半透明面，尚未实现。
- **多面体**（M15，[晶体学设计稿](crystallography-model.md) 5.6 节）：`Scene::polyhedra` 里每个 `Polyhedron` 是一组顶点、从外面看逆时针的三角形和一个颜色（线性 RGB 加不透明度）。每个三角形是一个实例（三个顶点加颜色，64 字节），顶点着色器按 `vertex_index` 取角，平面着色，法向在视空间里朝向相机的一侧，所以远处面的内侧、平面多边形的两面都有光照。
  - **次序**：在不透明的球、键、线段之后画，读深度、不写深度，颜色按 src·α + dst·(1 − α) 混合（`BlendState::ALPHA_BLENDING`），关掉 alpha-to-coverage（否则不透明度会变成覆盖的采样数），MSAA 照样平滑三角形的边。高亮圈在它之后画，被选中的原子在多面体里面也看得清。
  - **从远到近排序**：每次出帧时如果相机的视图矩阵变了，就在 CPU 上重新排：多面体按顶点平均位置的视空间深度从远到近，每个多面体内部先画背向相机的面、再画朝向相机的面（正交投影下按面法向的视空间 z 判断），凸多面体在自身内部因此完全正确；排好的实例整块重新上传。多面体之间按中心排序是近似：两个不相交的凸体，中心更远的那个偶尔有一部分在前面，这时混合的先后反了。共棱、共顶点的八面体框架和四面体网络在截图巡览里看不出错。相机不动时（换高亮、悬停）不重排。
  - **为什么不用顺序无关透明（OIT）**：加权混合 OIT（McGuire 与 Bavoil 2013）要两张额外的附件（RGBA16F 的累积和 R8 的透过率），在 MSAA 4× 下也要多重采样，再加一个合成通道。1792 × 1600 时这两张附件约 100 MB 显存（每像素 4 个样本 × 9 字节），每帧的带宽随分辨率增长，而且浮点附件的解析要单独处理。它的权重按深度估计遮挡，相互重叠的面颜色接近"平均"，前后层次不如排序清楚。多面体都是凸的、彼此基本不相交，排序已经够用，代价只在 CPU 上（8.6 节）。以后晶面（M16）与多面体相交、排序误差明显时，再考虑 OIT 或逐像素链表。
  - **棱线**：多面体的棱是普通线段（与晶胞边同一条管线），由 `mw-structure` 加进场景，颜色是中心原子颜色乘 0.45，宽 1 逻辑像素。线段在面之前画并写深度，所以面不会盖住它；背面的棱透过前面的面看得见。
  - **拾取**：多面体不参与拾取，ID 通道里不画，点击穿过多面体选中后面或里面的原子（中心原子、顶点上的配体）。以后要选中多面体，加一个 ID 类别即可（5.4 节）。
- **抗锯齿**：MSAA 4×。环境光遮蔽（SSAO）作为可选效果，以后再加。
- **已知代价**：写 `frag_depth` 会关闭提前深度测试（early-z），被挡住的片元也要跑完整个着色器。原子和键都很密时，这部分开销随重叠层数增长（8.2 节的 10 万原子 + 30 万键）。可以考虑的办法：把四边形放在球或圆柱离相机最近的平面上，再用保守深度（conservative depth）声明写出的深度只会更远，让硬件保留提前测试。

## 6. 零拷贝路线：方案 C 与方案 F

只有当实测证明方案 A 不够用时才考虑零拷贝。方案 C 是给 GPUI 打补丁，加一个外部纹理图元，按平台独立推进：

| 平台 | 做法 | 需要改的 crate | 难度 |
|---|---|---|---|
| Linux / Web | 通过 `Window` 暴露 GPUI 的 wgpu `Device` / `Queue`；新增"wgpu 纹理"图元，复用 wgpu 渲染器里已经创建好的 surfaces 管线，画一个带纹理的四边形 | `gpui-pre`、`gpui-pre-wgpu` | 低：同一个设备、同一个队列，不需要跨 API 同步 |
| macOS | 渲染器（wgpu 的 Metal 后端）渲染到由 IOSurface 支持的纹理；在 GPUI Metal 渲染器的 `draw_surfaces` 里，加一个 `kCVPixelFormatType_32BGRA` 单平面格式的分支 | `gpui-pre`、`gpui-pre-apple` | 中：两个 Metal 设备之间要做同步，IOSurface 要轮换；还需确认 wgpu 29 的 hal 互操作接口 |
| Windows | wgpu（D3D12）渲染到可共享的资源，GPUI（D3D11）打开共享句柄后绘制 | `gpui-pre`、`gpui-pre-windows` | 高：要跨 API 共享资源并用围栏同步。默认继续使用方案 A |

**补丁的维护策略**：

- 用 `[patch.crates-io]` 指向自己维护的 `gpui-pre-*` 分支。
- 补丁尽量小，争取提交给上游（Zed / GPUI Kit）。
- 每次升级 GPUI Kit，都按附录清单复核。

### 6.2 方案 F：底层合成（不改 GPUI）

> 2026-10-23 已做可行性论证，详见[可行性报告](viewport-underlay-feasibility.md)：macOS 做了原型并实测，Windows 和 Wayland 只核查了源码。**结论是现在不采用**，下面的平台表和风险已按报告更新。

**做法**：

1. wgpu 渲染到一个原生子图层上，这个子图层不是 GPUI 的。
2. 把子图层放在 GPUI 内容的下面。
3. GPUI 窗口用透明背景，界面照常画不透明的主题背景，只在视口区域留出透明的洞。
4. 由系统合成器把两层叠起来，画面完全不经过 CPU。

**和方案 B 的区别**：方案 B 的原生视图盖在 GPUI 上面，所以弹层会被挡住；方案 F 的原生图层在下面，GPUI 的测量标注、浮动工具条、对话框和通知自然叠在 3D 画面上，满足第 2 节的约束。

**分工：wgpu 负责渲染和送显，平台胶水负责图层放在哪里。**

- **wgpu 负责的部分**：
  - `mw-crystal-render` 的全部渲染代码保持纯 wgpu，三个平台共用；
  - 绘制目标由 wgpu 在原生对象上创建（3.5 节），提交和送显也都是 wgpu 调用，不直接写 Metal 或 Direct3D；
  - 拾取不变，仍是离屏渲染一小块 ID 纹理再回读（5.4 节）。
- **平台胶水负责的部分**：建子图层、把它放在 GPUI 下面、跟着布局更新位置和大小、和 GPUI 同步提交。这些是窗口系统和合成器的接口，不是图形接口，wgpu 不管。不能直接在 GPUI 的窗口上再建一个 wgpu 绘制目标：同一个窗口通常只能有一个交换链（Vulkan 下尤其如此），所以必须先建独立的子对象。

| 平台 | 胶水要做的事 | 接口 | 难度 |
|---|---|---|---|
| Windows | 建一个非顶层的 DirectComposition 目标和视觉对象，wgpu（DX12 后端）在上面渲染；设置偏移和裁剪，提交。GPUI 的合成交换链总是预乘 alpha，透明时清成 0。两个设备各自提交，没有跨设备的原子提交，预计布局动画时会偶发错开一帧 | DirectComposition（windows-rs） | 中；**源码上可行，未实测**，同步要在实机上量 |
| Linux Wayland | 在 GPUI 的 Wayland 连接上另开事件队列，自己绑定 `wl_subcompositor`，建一个子表面放在 GPUI 表面的下面；用 `wp_viewport` 处理分数缩放；wgpu 走 Vulkan。子表面的位置、层叠和内容在同步模式下随 GPUI 的下一次提交一起生效 | wayland-client | 中；**源码上可行，未实测**。三个平台里同步条件最好，风险是 Vulkan 送显节流和部分驱动不支持预乘 alpha |
| macOS | GPUI 的 `GPUIView` 只是窗口内容视图的普通子视图（3.5 节），在内容视图里、`GPUIView` 的下面插一个承载图层的兄弟视图即可，不碰系统私有视图；鼠标、拖放、输入法和焦点仍归 GPUI。必须自己建 `CAMetalLayer`：`create_surface(window)` 会拿到 GPUI 自己的图层。`presentsWithTransaction` 可以自己设，wgpu 不覆盖。GPUI Kit 的根视图要清掉背景，各区域自己画背景 | AppKit、Core Animation（objc2） | 中；**可行但有风险，已实测**：静止和匀速旋转时两层完全对齐；GPUI 平时异步送显，外部图层没法和它原子提交，侧栏动画时约 1.5 % 的帧边缘错开一帧（底色设成视口背景色可以掩盖）；主线程取 drawable 偶尔阻塞 7–20 ms，量产要改到渲染线程 |
| Linux X11 | 子窗口只能画在上面 | — | 做不到，继续用方案 A |

每个平台的胶水大约几百行，藏在同一个接口后面：设置位置和大小、显示或隐藏、提交。不支持的平台，以及无界面、截图巡览和界面集成测试，都退回方案 A。

**风险**：

- **两层不同步**：拖动面板、收起侧栏时，GPUI 和子图层各自提交，可能错开一帧，边缘出现缝隙或重叠。macOS 实测约 1.5 % 的帧（上表）；只有 Wayland 能真正一起提交。拖动改变窗口大小时 macOS 理论上同步，尚未实测。
- **标注与画面**：macOS 原型在 GPUI 的同一轮里送显，匀速旋转时 3D 画面和 GPUI 画的标注实测是同一帧。顺带发现方案 A 的标注反而比画面快 1–2 帧，因为投影用的是当前相机（报告 4.5 节）；现在已改为按屏幕上那一帧的相机投影（8.3 节）。
- **主线程阻塞**：`CAMetalLayer` 的 drawable 归还得晚时，取下一个会在界面线程上等 7–20 ms；渲染线程能解决，但会削弱和 GPUI 同轮送显带来的同步。
- **整个窗口变透明**：系统合成的开销会增加；GPUI Kit 的组件都要保证自己画了不透明背景，否则会透出下面的内容。
- **截图和测试拍不到 3D 画面**：`render_to_image` 只拍到 GPUI 这一层，视口位置是个空洞，所以测试必须走方案 A。
- **裁剪和移动**：子图层是矩形，圆角要单独加遮罩；视口所在区域能滚动时，图层要跟着移动。
- **显卡选择**：双显卡电脑上，wgpu 要选和 GPUI 相同的 GPU（用 `Window::gpu_specs` 匹配），否则合成时可能跨 GPU 拷贝。

**收益**：和方案 C 相同。每帧省掉回读、拷贝和上传，在 1792×1600 下约 1.5–4 ms（8.1 节），延迟也少大约一帧。到 4K 或 120 Hz 屏幕，差别更明显。

**工作量**：三个平台合计约三周（报告第 5 节），另有每次升级 GPUI Kit 时的复核（报告第 8 节的清单）。

**何时启动**：只有在 4K、120 Hz 或 Linux、Windows 上实测，证明方案 A 及其优化不够用，而方案 C 又进不了上游时才启动。顺序：

1. **Linux Wayland**：同步条件最好，GPUI 在 Linux 上本来就用 wgpu。
2. **Windows**：分层是系统支持的，胶水简单，但同步要先在实机上量。
3. **macOS**：先等上游 #61291（6.1 节），那样能在 GPUI 自己的帧里合成，天然同步，窗口也不必透明；等不到再用原型的做法，并先解决 drawable 阻塞。

启动前先补完原型的三项测量：拖动改变窗口大小时的同步、屏幕常亮下两种方案的完整基准、渲染线程送显后的同步和界面线程开销。原型代码在分支 `claude/underlay-feasibility-5c0830`（提交 `54641c9`），没有合并进 main。

### 6.3 不采用：用 unsafe 访问 GPUI 内部，或改用 C

- **按内存偏移读写 GPUI 的私有字段**（例如拿到它的渲染器或 wgpu 设备）：Rust 不保证普通结构体的布局，这本身就是未定义行为；`gpui-pre` 每次升级都可能改变布局，出错时表现为难以排查的随机崩溃，比维护补丁更糟。
- **改用 C 语言**：Metal、Core Animation、Direct3D、DirectComposition、Wayland 在 Rust 里都能直接调用（objc2、windows-rs、wayland-client）。C 不会多出任何能力，只会多一套工具链。
- **只在统一内存上省一次拷贝**：让 wgpu 渲染到 IOSurface 支持的纹理，CPU 直接读，可以省掉拷到暂存缓冲区那一步，但 CPU 拷贝和 GPUI 上传仍然少不了。收益有限，不值得为它引入 unsafe。

## 7. 不采用 Bevy 的理由

- **嵌入问题不会消失**：Bevy 要自己掌控事件循环和窗口，放进 GPUI 一样要走方案 A 或 C。
- **wgpu 版本很可能对不上**：Bevy 的 wgpu 版本跟着 Bevy 版本走，很可能和 GPUI 的 wgpu 29 不一致。这样就无法共用设备，依赖树里还会出现两份 wgpu。
- **会出现两份状态**：Bevy 的 ECS 世界和文档模型是两份数据，需要持续同步，这和"结构是唯一事实来源"的设计冲突。
- **能力用不上**：晶体渲染需要的是专用管线（impostor、拾取 ID、标注投影）。Bevy 的 PBR 材质、场景和资源系统基本用不上，却要承担它的编译时间、二进制体积和每个大版本的升级成本。

## 8. PoC 计划

**范围**：一个最小的 GPUI Kit 应用，左侧是面板，中间是视口，右侧是属性面板。视口渲染合成的球体阵列（1 千、1 万、10 万个原子），可以用鼠标拖拽旋转。不接入真实的晶体模型。

**测量项**（先测 macOS，再测 Linux 和 Windows）：

| 指标 | 条件 |
|---|---|
| 每帧耗时分解：渲染、拷贝与映射等待、构造 `RenderImage`、GPUI 绘制 | 视口物理分辨率分别为 1280×800、2560×1600、3840×2160 |
| 连续旋转时的帧率和输入延迟（以帧计） | 交互缩放系数分别为 1.0 和 0.5 |
| 连续旋转 10 分钟时的图集内存和进程内存 | 必须保持平稳 |
| 静止时的 CPU / GPU 占用 | 应接近 0 |

**功能检查**：

- 命令面板、右键菜单、Popover、Tooltip 盖在视口上时显示正常。
- HiDPI 下像素精确；缩放窗口、在缩放比不同的显示器之间拖动窗口都正常。
- 深浅色主题切换正常；双显卡机器上适配器匹配正确。
- 测出 1 像素拾取回读的延迟。

**验收建议**（阈值待 PoC 后确认）：在 2560×1600、1 万个原子、交互缩放系数 0.5 的条件下，如果连续旋转能稳定在 60 fps，并且停止交互后 150 ms 内能出全分辨率帧，该平台就保持方案 A；达不到时，该平台进入方案 C。

### 8.1 macOS 实测结果（2026-10-22）

代码：渲染器在 `crates/mw-crystal-render`，PoC 应用在 `apps/viewport-poc`。复现命令：

```bash
VIEWPORT_POC_BENCH=1 cargo run -p viewport-poc
```

**环境**：

- Apple M5（统一内存），内建屏刷新率 60 Hz，所以帧率上限就是 60 fps。
- GPUI Kit 0.8.0 / `gpui-pre` 0.3.9，wgpu 29.0.4（Metal 后端）。
- debug 构建，但 GPUI 和 wgpu 按 GPUI Kit 安装指南以 `opt-level = 3` 编译。
- 窗口 1440×900 逻辑像素，视口 896×800 逻辑像素，即 1792×1600 物理像素。
- 自动旋转，每档预热 1 秒、测量 5 秒；时间是测量期间的平均值，单位 ms。

| 原子数 | 渲染尺寸 | 每帧数据 | 显示帧率 | 编码提交 | GPU + 回读等待 | 内存拷贝 | GPUI 绘制（含上传） | 请求 → 出图 |
|---|---|---|---|---|---|---|---|---|
| 1 千 | 1792×1600 | 11.5 MB | 60 | 0.40 | 4.3 | 1.08 | 2.42 | 5.8 |
| 1 千 | 896×800 | 2.9 MB | 60 | 1.03 | 5.1 | 0.29 | 0.86 | 6.4 |
| 1 万 | 1792×1600 | 11.5 MB | 60 | 0.41 | 4.4 | 0.93 | 2.32 | 5.7 |
| 1 万 | 896×800 | 2.9 MB | 60 | 0.95 | 4.9 | 0.28 | 0.87 | 6.2 |
| 10 万 | 1792×1600 | 11.5 MB | 60 | 0.43–0.45 | 7.6–9.4 | 0.92–0.96 | 1.90–2.03 | 9.0–10.8 |
| 10 万 | 896×800 | 2.9 MB | 60 | 1.01 | 5.1 | 0.28 | 0.83 | 6.5 |

10 万原子全分辨率一行是两轮测量的范围。

**结论**：

- **所有档位都跑满了显示刷新率。** UI 线程每帧花在视口上的时间约 1–3 ms（编码提交 + GPUI 绘制上传），等待和拷贝都在后台线程。
- **从相机变化到新图像就绪 6–11 ms**，大约比直接上屏多一帧延迟。
- **"GPU + 回读等待"有一个 4–5 ms 的下限**，和分辨率关系不大，主要是从提交到完成的调度延迟；只有 10 万原子全分辨率时它才明显上升。
- **按上面的验收建议，macOS 保持方案 A，暂不需要方案 C。** 验收条件要求的渲染尺寸（2560×1600 缩放 0.5，即 1280×800）比本次的 896×800 略大，但本次全分辨率 1792×1600 也稳定 60 fps。
- **外推（未实测）**：每帧数据量与像素数成正比。2560×1600 全分辨率约 16.4 MB，按本次数据线性外推，拷贝约 1.4 ms、绘制上传约 3.4 ms，仍在 60 Hz 的 16.7 ms 预算内；120 Hz（8.3 ms 预算）下全分辨率会比较紧，交互时降到 50% 即可。

**测量中发现并修复的问题**：

- **多余的渲染**：每次重绘都登记一次"下一帧推进旋转"的回调，导致一帧内推进多次，完成的帧比显示的多 20–60%。现在同一时刻只登记一个回调，完成数与显示数一致。
- **掉帧**：前两轮在最后一档（10 万原子、50%）掉到 8.5 fps 和 1.5 fps。第三轮把这一档放到最前面、窗口一直在前台，稳定 60 fps。判断是测到最后时窗口被遮挡或切到后台，系统降低了刷新；前两轮没有记录窗口状态，不能完全确认。基准模式现在会记录测量期间窗口是否失去过焦点（`window_lost_focus`）。

**还没有验证的**：

- GPUI 弹层（Tooltip、Popover）盖在视口上的实际效果、HiDPI 下是否发虚、缩放窗口、跨显示器拖动。这些需要人工在窗口里检查（终端没有屏幕录制权限，无法自动截图）。渲染器本身的输出已用 `cargo run -p mw-crystal-render --example snapshot` 存成 PNG 检查过。
- 120 Hz 显示器，以及 2560×1600 以上的视口。
- Linux、Windows。
- 双显卡机器上的适配器匹配（本机只有一块 GPU）。
- 拾取（ID 纹理）当时还没有实现，见 8.2 节。

### 8.2 M3 复测（2026-10-22）

M3 加入了键、线段、高亮圈三条管线和单独的 ID 通道，用同一个 PoC 复测。PoC 增加了两项：

- 可以给合成负载加上键：相邻格点之间各一根，每个原子约 3 根。
- 每档测完后计时 20 次"相机刚变过"的拾取（要先重画 ID 纹理）和 20 次"相机没变"的拾取（只拷贝 9 × 9 像素），都在视口中心，从发出请求到结果回到 CPU。这两项在 UI 线程上同步等待，只在两档之间跑。

```bash
VIEWPORT_POC_BENCH=1 cargo run -p viewport-poc
```

单测某几档时可以写成 `VIEWPORT_POC_BENCH=1000:50,10000:100:bonds`（原子数:渲染比例[:bonds]）。

**环境**与 8.1 节相同：Apple M5，内建屏 60 Hz，窗口 1440 × 900、视口 1792 × 1600 物理像素，debug 构建（GPUI 和 wgpu 为 `opt-level = 3`）。

**测量条件比 8.1 节差**：测量期间这台机器在被使用，PoC 窗口多次失去焦点。失去焦点的档位帧率掉到 0.4–9 fps，数据作废；下表只用窗口一直在前台的档位，来自 4 次运行，同一档有多次有效数据时给出范围。PoC 启动后的第一档几乎总是失去焦点，单独测几档时可以在前面加一个不计数的档（如 `1000:50,1000:50,...`）。

| 1 千原子 | 1792×1600 | 60 | 0.42–0.43 | 3.9–4.3 | 0.54–0.65 | 1.8–1.9 | 5.0–6.1 | 1.5–2.8 | 1.3 |
| 1 千原子 | 896×800 | 60 | 0.43–0.60 | 2.3–7.7 | 0.15–0.27 | 0.5–0.7 | 2.9–8.6 | 1.5–1.7 | 1.3 |
| 1 万原子 | 1792×1600 | 59 | 0.40 | 6.5 | 0.81 | 1.9 | 7.8 | 4.5 | 1.4 |
| 1 万原子 | 896×800 | 60 | 0.60 | 3.5 | 0.25 | 0.7 | 4.4 | 1.8 | 1.3 |
| 10 万原子 | 1792×1600 | 60 | 0.39–1.43 | 8.0 | 0.41–0.89 | 1.2–1.9 | 9.3–12.4 | 4.0–4.4 | 1.3 |
| 10 万原子 | 896×800 | 60 | 0.52–1.34 | 6.1–8.3 | 0.10–0.26 | 0.3–0.6 | 8.5–9.1 | 3.6–4.2 | 1.2–1.3 |
| 1 千原子 + 3 千键 | 1792×1600 | 60 | 0.40 | 5.0 | 0.76 | 1.8 | 6.2 | 2.9 | 1.3 |
| 1 万原子 + 3 万键 | 1792×1600 | 60 | 0.42 | 10.8 | 0.76 | 1.9 | 12.9 | 5.1 | 1.3 |
| 10 万原子 + 30 万键 | 1792×1600 | 29–36 | 9.6–12.3 | 16.7–21.7 | 0.6–1.5 | 1.9–4.4 | 38–73 | 8.0 | 1.3–1.4 |

时间单位 ms。10 万原子 896×800 一行的 8.3 ms 是四边形外扩 1.5 像素时测的，改成 0.75 像素后为 6.1 ms（见下）。10 万原子 + 30 万键在 896×800 下两次都失去焦点，没有有效数据。

**结论**：

- **只有原子时没有退化。** 所有档位仍跑满 60 fps，UI 线程每帧花在视口上的时间仍是 1–3 ms，与 8.1 节在同一量级。"GPU + 回读等待"的波动比 8.1 节大（同一档 2.3–7.7 ms），和机器在被使用一致，不能据此判断变快或变慢。
- **满足路线图 M3 的验收条件**（1 万原子 60 fps 不退化）：1 万原子在两种尺寸下都是 60 fps，再加 3 万根键在全分辨率下也是 60 fps，GPU 等待从约 6 ms 升到约 11 ms。
- **10 万原子 + 30 万键在全分辨率下受 GPU 限制**，只有 29–36 fps，而且提交本身在 UI 线程上阻塞 10–12 ms（GPU 忙不过来时提交要等）。这个量级远超 v0.1 的显示范围（一个晶胞，通常几十到几百个原子），但 v0.3 的显示范围和大超胞会碰到。办法按顺序是：落实 5.3 节的交互缩放（交互时 0.5，已在 8.3 节落实）；用保守深度保住提前深度测试（5.6 节）。
- **拾取延迟**：相机没变时约 1.3 ms，与负载无关，主要是提交和映射的调度开销；相机刚变过时要先重画 ID 纹理，1.5–8 ms，随负载增长。悬停在静止画面上只走前一种，都在一帧之内。这两组数字包含等待之前在途的画面帧。
- **测量中修复的问题**：最初把球的四边形外扩了 1.5 个像素。10 万原子在 896×800 下每个原子只有几个像素，外扩占了四边形的大半，GPU 等待从 8.1 节的 5.1 ms 升到 8.3 ms。覆盖率过渡带只延伸到轮廓外半个像素，现在球、键、高亮圈都只外扩 0.75 像素，复测为 6.1 ms。
- **未查明**：多次运行里"完成帧数"比"显示帧数"多 30–80%（8.1 节修复后两者一致）。PoC 的出帧调度在 M3 里没有改动；同一次运行的第一轮全量测量里两者仍基本一致（60 对 62–65），怀疑与测量时机器的状态有关，没有进一步确认。

### 8.3 方案 A 内减少往返（2026-10-23）

零拷贝短期不做（第 6 节），这次只在方案 A 的框架内减少 GPU → CPU → GPU 的往返：

| 改动 | 位置 | 怎么验证 |
|---|---|---|
| 一轮改动只出一帧（5.3 节第 1 条） | `mw-viewport` | 界面集成测试 `an_edit_renders_one_frame`：编辑、撤销各提交一帧，以前各两帧 |
| 拖动和缩放时按 0.5 倍渲染，停下 150 ms 后补全分辨率（5.3 节） | `mw-viewport`；渲染器为两种尺寸各留一套目标 | `dragging_settles_into_a_full_frame`：每次移动一帧，降分辨率期间 `is_current` 为假，时钟走过 150 ms 后补一帧 |
| 悬停圈画在画面上面，悬停不出帧（5.5 节） | `mw-viewport` | `hovering_renders_no_frame`：指向原子、再移开，都不提交帧 |
| 过时帧不拷贝（5.3 节第 5 条） | `mw-crystal-render` | 单元测试 `superseded_frames_skip_the_copy`；PoC 基准输出新增 `skipped_fps` |
| 标注用屏幕上那一帧的相机（5.3 节第 8 条） | `mw-viewport` | `labels_follow_the_image_on_screen`：新相机的帧在途时标签不动，帧到了才移动 |
| 每行没有补齐时整块拷贝 | `mw-crystal-render` | 基准的"内存拷贝" |

四个界面测试都做过反证：把对应的旧行为改回去（立即提交、悬停时出帧、按当前相机投影、拖动时不降分辨率），各自的测试就失败。

**基准**：PoC 有自己的出帧循环（`apps/viewport-poc`），只用到渲染器，所以它能比较的是渲染器层面的改动；`mw-viewport` 的改动靠上面的帧数测试验证，代价按基准里对应的档位估算（见后文）。环境与 8.1 节相同（Apple M5、内建屏 60 Hz、视口 1792 × 1600 物理像素、debug 构建）。

这次测量时 Firefox 在后台占用 GPU，不少档位在两个版本上都被限在 30 fps，窗口并没有失去焦点。所以改动前后的程序交替各跑三轮，取中位数，丢掉每轮第一档：

```bash
VIEWPORT_POC_BENCH=1000:100,1000:100,10000:100,10000:50,100000:100,100000:50,10000:100:bonds cargo run -p viewport-poc
```

| 负载 | 渲染尺寸 | 显示帧率 | 编码提交 | GPU + 回读等待 | 内存拷贝 | GPUI 绘制 | 请求 → 出图 |
|---|---|---|---|---|---|---|---|
| 1 千原子 | 1792×1600 | 30 → 30 | 0.71 → 0.76 | 2.68 → 2.68 | 1.13 → 0.81 | 2.87 → 3.05 | 4.58 → 4.31 |
| 1 万原子 | 1792×1600 | 30 → 30 | 0.57 → 0.57 | 4.68 → 4.52 | 1.08 → 0.70 | 2.57 → 2.65 | 6.37 → 5.82 |
| 1 万原子 | 896×800 | 30 → 30 | 1.03 → 1.07 | 2.72 → 2.75 | 0.43 → 0.22 | 0.97 → 0.99 | 4.25 → 4.10 |
| 10 万原子 | 1792×1600 | 60 → 60 | 0.46 → 0.44 | 8.81 → 7.54 | 1.00 → 0.66 | 1.96 → 2.00 | 10.30 → 8.68 |
| 10 万原子 | 896×800 | 60 → 60 | 0.82 → 0.71 | 6.62 → 6.58 | 0.28 → 0.17 | 0.80 → 0.75 | 7.76 → 7.62 |
| 1 万原子 + 3 万键 | 1792×1600 | 60 → 60 | 0.47 → 0.46 | 11.85 → 12.10 | 0.80 → 0.65 | 1.88 → 1.96 | 13.15 → 13.27 |

时间单位 ms，"改动前 → 改动后"。

**结论**：

- **渲染器层面的改动只影响后台线程。** 内存拷贝在每一档都降了 20–50%，三轮交替的方向一致；比微基准的预计大（11.5 MB 逐行拷贝 0.40 ms、整块 0.35 ms），原因没有查明。界面线程上的编码提交和 GPUI 绘制不变，帧率不变；请求 → 出图在 GPU 不是瓶颈的档位略降，其余在噪声之内。
- **过时帧在 PoC 里很少见。** 自动旋转每个显示帧只请求一帧，`skipped_fps` 多数为 0，最多 10.6。真正受益的是拖动时鼠标事件比出帧快、两帧在途的情形。8.2 节"完成帧数比显示帧数多"的现象在改动前后都出现过，这些帧的拷贝没有被跳过，所以它们不是被超越的帧：两帧都在前一帧完成之后才提交，只是在同一个显示周期里先后完成。原因仍未查明。
- **交互降分辨率的收益**按同一组数据的 50% 档估算。1 万原子时，GPUI 绘制（界面线程）从 2.65 降到 0.99 ms，内存拷贝从 0.70 降到 0.22 ms，请求 → 出图从 5.82 降到 4.10 ms。GPU 受限的 10 万原子，请求 → 出图从 8.68 降到 7.62 ms。
- **一轮一帧、悬停不出帧**各省掉整整一帧：一次渲染，一次回读（全分辨率 11.5 MB），一次上传（界面线程约 2–3 ms）。悬停以前在鼠标从一个原子移到另一个时就出一帧，现在只重画 GPUI 的一个圆环。
- **标注不再领先画面。** 没有做像素级的自动测量，语义由 `labels_follow_the_image_on_screen` 保证。截图巡览里，原子的位置按屏幕上那一帧算，所以转动视图的拖动单独放在一步里，等新画面到了再点选（`_turn-rutile`）。

**评估后没有做的**：

- **渲染宽度对齐到 64 像素**：微基准（M5，11.5 MB）里宽 1791 时逐行拷贝 0.57 ms，对齐成 1792 后整块拷贝约 0.41 ms，在后台线程上省 0.15 ms。代价是每帧多渲染、多上传最多 63 列（1792 宽时约 3.5%），上传在界面线程上，得不偿失。基准用的宽度 1792 和 896 本来就是 64 的倍数，已经整块拷贝。
- **复用 CPU 缓冲区**：做不到。像素交给 `RenderImage` 后归它所有（`data` 是私有字段，没有取回的接口），微基准里复用 `Vec` 也只省约 0.03 ms。GPU 端的暂存缓冲本来就复用，现在不同尺寸的可以并存。

### 8.4 Linux 与 Windows（待测）

M13 要在 Linux 和 Windows 实机上运行应用并重测视口，结果按 8.1、8.2 节的格式记在这里。CI（开发指南 2.1 节）只说明在软件适配器上能编译、测试能通过；运行器没有显示器，窗口系统、合成器、真实 GPU 和帧率都不在它的范围内。

1. **记下环境**：系统版本；显卡型号和驱动版本；显示器分辨率、刷新率和缩放比；Linux 上是 Wayland 还是 X11（`echo $XDG_SESSION_TYPE`）。
2. **运行应用**，日志里有渲染器选的适配器（`renderer adapter:` 一行）和 GPUI 自己选的适配器：

   ```bash
   RUST_LOG=info cargo run --bin materials-workbench
   ```

   Windows 的 PowerShell 里先 `$env:RUST_LOG="info"`。走一遍：打开示例项目里的金红石，拖动旋转、滚轮缩放；单击、Ctrl-单击、⇧-单击原子；测量距离；改一个晶胞参数，Ctrl+Z 撤销、Ctrl+Shift+Z 重做；V 进移动模式拖一个原子，按住 Alt 脱离特殊位置；Ctrl+K 命令面板；Ctrl+S 保存，关闭项目再从最近项目打开；用命令面板切换深色模式和英文界面；拖动改变窗口大小。记下不对的地方，最好带截图。缩放比不是 100 % 时看原子边缘和文字是否发虚。
3. **视口基准**：窗口保持在前台、不要动鼠标，约 1 分钟后自动退出，把输出整个保存下来：

   ```bash
   VIEWPORT_POC_BENCH=1 cargo run -p viewport-poc 2>&1 | tee bench.txt
   ```

   Windows 的 PowerShell 里先 `$env:VIEWPORT_POC_BENCH="1"`，再 `cargo run -p viewport-poc 2>&1 | Tee-Object bench.txt`。输出里 `window_lost_focus=true` 的档位作废；第一档常常失去焦点，可以按 8.2 节的写法在前面加一个不计数的档重测。PoC 窗口右侧"设备"一栏写着渲染器和 GPUI 各用的适配器，截一张图或抄下来；有两块显卡的机器尤其要看两者是不是同一块。
4. **（可选）连接运行中的应用**：设置里打开"允许 MCP 客户端连接"，再在另一个终端运行 `RUST_LOG=info cargo run --bin materials-workbench -- mcp --allow crates/mw-project-file/samples`，标准错误里应有 `connected to the running application`；在终端里按 Ctrl+D（Windows 上 Ctrl+Z 回车）结束输入，命令应当马上退出。

把第 1 步的环境、第 2 步发现的问题和 `bench.txt` 交回来，整理进本节和架构文档第 10 节的 M13 行。

### 8.5 M14 大显示范围（2026-10-24）

显示范围（晶体学设计稿 5.5 节）让一个结构画出成千上万个原子。这次量的是界面线程和后台线程上的计算，负载是金红石的 n × n × n 个晶胞（带边界原子），环境与 8.1 节相同（Apple M5）。时间单位 ms，"debug"是开发时的构建（GPUI 和 wgpu 为 `opt-level = 3`，本仓库的 crate 不优化），"release"是 `--release`：

| 范围 | 原子 | 键 | 显示原子与键（`Derived::display`） | 组场景（`scene::draw`） | 拖动预览（每次指针移动） |
|---|---|---|---|---|---|
| 10 × 10 × 10 | 6 531 | 12 200 | 12.1 / 1.4 | 2.7 / 0.5 | 13.1 / 1.5 |
| 15 × 15 × 15 | 21 421 | 40 950 | 31.6 / 3.2 | 5.2 / 0.8 | 36.3 / 4.0 |
| 20 × 20 × 20 | 50 061 | 96 800 | 71.3 / 6.2 | 12.2 / 1.7 | 84.2 / 7.0 |

每格是"debug / release"。派生数据本身（轨道、键、对称性分析）只依赖一个晶胞，不随范围变化，约 0.6 / 0.09 ms。

**做法**：

- 超过 5 000 个原子的范围在后台线程上算显示原子（`mw-structure/src/display_range.rs`），算好之前视口保持原来的场景，信息标签显示转圈和"正在准备…"；编辑后同样如此。组场景和上传留在界面线程上，debug 下 5 万个原子约 12 ms。
- 拖动预览在这种范围里也放到后台，一次只算一个：算的时候到来的指针移动合并，算完立刻按最新位置再算一次（`moving.rs`）。debug 下 2 万个原子以上每次要 36–84 ms，放在界面线程上会让拖动和其他交互一起卡顿。
- 组场景时元素样式按元素查一次，不再每个原子在 109 个元素里线性查找。
- 上限 100 000 个原子（晶体学设计稿 5.5 节），依据是 8.2 节：10 万原子加 30 万键全分辨率只有 29–36 fps。

**无窗口出帧**：界面集成测试的窗口（视口 928 × 752 逻辑像素，debug）里每次换相机后等新帧到位，30 帧取平均：一个晶胞 17.7 ms，10 × 10 × 10 为 18.5 ms，15 × 15 × 15 为 23.8 ms，20 × 20 × 20 为 28.1 ms。测试里的 17.7 ms 大多是测试框架自己的绘制和轮询，与负载无关；10 × 10 × 10 只比一个晶胞多 0.8 ms。设置范围到第一帧到位：10 × 10 × 10 为 62 ms，20 × 20 × 20 为 502 ms（debug，含后台计算、组场景、上传和测试框架的开销）。

**屏幕上的帧率没有测到**：这次跑 `VIEWPORT_POC_BENCH=6531:100:bonds,6531:50:bonds,21421:100:bonds,50061:100:bonds,50061:50:bonds cargo run -p viewport-poc` 时 PoC 的窗口没有被系统绘制（进程 10 分钟只用了 0.5 s CPU，测量时是凌晨，显示器多半已关），没有数据。按 8.2 节的结果估计：10 × 10 × 10（6 531 原子、12 200 键）比"1 万原子 + 3 万键"轻，后者全分辨率 60 fps；20 × 20 × 20（5 万原子、9.7 万键）介于它与"10 万原子 + 30 万键"（29–36 fps）之间。要在窗口可见时用上面的命令补测（合成负载每个原子约 3 根键，比金红石的约 1.9 根重），M13 在三个平台上重测时一并做。

### 8.6 M15 多面体（2026-10-24）

多面体模型（5.6 节，晶体学设计稿 5.6 节）在原子之外加了三笔开销：算凸包和补画的配体（后台），组场景时多出的多面体和棱线（界面线程），以及相机转动时每一帧在 CPU 上重新排序、上传（界面线程上的"编码提交"）。负载是 10 × 10 × 10 金红石：7 897 个原子（6 531 个范围里的，加 1 366 个补画的 O），2 331 个八面体（18 648 个三角形），27 984 条线段（棱和晶胞边）。环境与 8.1 节相同（Apple M5）；测量时机器上有别的编译在跑，同一档几次之间差到两倍，下面给出范围。时间单位 ms，"debug / release"同 8.5 节。

| 步骤 | 在哪里 | debug | release | 对照 |
|---|---|---|---|---|
| 显示原子与多面体（`Displayed::with_polyhedra`） | 后台线程（超过 5 000 个原子时） | 79 | 9.7 | 不带多面体 12.1 / 1.4（8.5 节） |
| 组场景（`scene::draw`） | 界面线程 | 30 | 1.5–3.4 | 不带多面体 2.7 / 0.5（8.5 节） |
| 设置范围到多面体算好、场景交给视口（界面集成测试，含测试框架的开销） | — | 277 | — | — |

转动相机时每一帧的耗时用渲染器的测量测试得到（`polyhedra_frame_timings`，开发指南第 2 节）：合成负载是同样数量的球、八面体和棱线，相机每帧转一点，每帧都要重新排序，30 帧取平均：

| 负载 | 渲染尺寸 | 编码提交（界面线程，含排序与上传）debug | 同 release | GPU + 回读等待 release |
|---|---|---|---|---|
| 只有 7 897 个球 | 896×800 | 0.15–0.25 | 0.06–0.12 | 1.6–2.6 |
| 只有 7 897 个球 | 1792×1600 | 0.17–0.26 | 0.03–0.07 | 1.3–3.9 |
| 加 2 331 个八面体和棱线 | 896×800 | 1.7–3.8 | 0.27–0.82 | 1.3–3.8 |
| 加 2 331 个八面体和棱线 | 1792×1600 | 1.7–4.5 | 0.30–1.31 | 2.5–7.0 |

**结论**：

- **计算在后台，不卡界面。** 超过 5 000 个原子的范围连同多面体一起在后台线程上算（M14 的机制，判断要不要重算时多看一项多面体的中心）；debug 下 10 × 10 × 10 约 80 ms，算好之前视口保持原来的画面。
- **组场景在界面线程上，debug 约 30 ms**，是不带多面体时的十倍，主要是近 2.8 万条棱线和每个多面体的几次小分配。只在范围、结构、显示模型或中心改变时发生一次，不随相机转动；release 下可以忽略。以后若要更大的范围，可以把组场景也挪到后台任务里。
- **转动时的排序与上传**：release 下每帧不到 1.5 ms，debug 下 2–4 ms，都在 60 Hz 的 16.7 ms 预算之内；相机不动时（换高亮、悬停）不重排。GPU 上的代价是半透明三角形的混合，全分辨率时 GPU 加回读的等待大约翻倍（1.3–3.9 → 2.5–7.0 ms）。
- **屏幕上的帧率没有测**：PoC 的出帧循环没有多面体负载，这次也没有在窗口里跑基准（会抢占前台窗口）。按上表，合成负载在全分辨率下每帧的 GPU 和界面线程时间加起来不到 10 ms，估计能保持 60 fps；与 8.5 节一起在窗口可见时补测，M13 在三个平台上重测时一并做。

## 9. 风险与待确认

| 项 | 说明 |
|---|---|
| `RenderImage` 的颜色约定 | 注释写的是 BGRA，还需要确认 sRGB 和预乘 alpha 的约定，避免颜色偏差 |
| 每帧新建 `RenderImage` 的图集开销 | `paint_image` 走精灵图集，需要确认高频替换时的上传开销和碎片情况 |
| GPUI Fast 后端 | GPUI Kit 的可选特性 `gpui-fast` 没有评估，不在本次选型范围内 |
| impostor 关闭提前深度测试 | 写 `frag_depth` 使被挡住的片元也要着色；10 万原子 + 30 万键在全分辨率下只有约 30 fps（8.2 节）。对策见 5.6 节 |
| 多面体之间的排序是近似 | 按多面体中心从远到近排（5.6 节），两个不相交的凸体偶尔次序反了，混合的颜色略有不同；共棱、共顶点的框架看不出。晶面（M16）与多面体相交时会更明显，那时再考虑顺序无关透明 |
| 方案 C 能否进入上游 | 同类提案（讨论 #60572、PR #60573）已被要求先定设计，三个半月没有维护者回复（6.1 节）。自己维护补丁要长期跟着 GPUI Kit 的版本走；进不了上游时，用不改 GPUI 的方案 F（6.2 节） |

## 附录：升级 GPUI Kit 时的复核清单

升级后，在新版 `gpui-pre-*` 的源码中检查以下几点：

1. `surface()` / `Window::paint_surface` 是否仍然只限 macOS / iOS，`PaintSurface` 的内容类型有没有变。
2. `gpui-pre-apple` 的 `draw_surfaces` 是否仍然只接受 YUV 4:2:0。
3. `gpui-pre-wgpu` 和 `gpui-pre-windows` 的 Surface 绘制是否仍然是空实现。
4. `gpui-pre-wgpu` 依赖的 wgpu 大版本——它决定 `mw-crystal-render` 用哪个版本的 wgpu。
5. `Window::paint_image`、`Window::drop_image` 和 `RenderImage` 的签名与格式说明有没有变化。
6. 是否出现了新的外部纹理或自定义渲染接口。如果有，重新评估方案 C。
7. 6.1 节所列上游 PR 和讨论的进展。#61291 合并后，macOS 可以经 `surface()` 走 BGRA 的 IOSurface 零拷贝。
8. 方案 F 依赖的接口（3.5 节）：GPUI 是否仍支持透明窗口背景、macOS 的 Metal 图层是否仍随之设为非不透明；`Window` 是否仍实现 `HasWindowHandle`；Windows 上 GPUI 是否仍只用顶层 DirectComposition 目标。完整清单见[可行性报告](viewport-underlay-feasibility.md)第 8 节。
